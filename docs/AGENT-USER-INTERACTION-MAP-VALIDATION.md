# Agent–User Interaction 地图场景验证说明

> **定位：面向项目分享的验证主文档**  
> **版本：v0.1**  
> **日期：2026-08-24**

## 一句话说明

我们不是在做一个“地图 Agent Demo”，而是把地图作为第一个实验场，验证：

> **当 Agent 进入一个持续变化的前端界面后，用户和 Agent 应该如何共同操作、共享状态和让渡控制权。**

最终希望形成的不是更多地图功能，而是三类可以复用的成果：

1. **可复用的交互模式（Interaction Patterns）**；
2. **可以指导产品设计的原则（Design Principles）**；
3. **每种模式明确的适用条件与边界（Boundaries）**。

---

## 1. 为什么要做这个验证

传统软件主要由用户直接操作界面；Agent 进入软件以后，用户和 Agent 都可能成为界面的操作者。

例如在地图中：

- Agent 可以定位、聚焦、高亮、展示路线；
- 用户也可以点击、拖动、选择、调整和取消；
- Agent 的动作会持续改变当前界面状态；
- 用户修改之后，Agent 还需要基于新的状态继续工作。

因此真正的问题已经不只是“Agent 能不能调用一个前端工具”，而是：

> **当人和 Agent 共同使用同一个有状态 GUI 时，谁在什么时候操作、用户如何理解变化、如何纠偏、哪些状态需要共享，以及什么时候应该把控制权交给另一方。**

这类问题仅靠接口设计或 Demo 跑通无法回答，需要通过实际交互逐步验证。

---

## 2. 为什么选择地图作为第一个实验场

地图不是最终研究对象，而是一个适合观察 Agent–User Interaction 的实验环境。

它有几个特点：

- **状态明显**：视口、图层、高亮、选择、路线都会持续保留；
- **用户可以直接操作**：点击、拖拽、框选、调整天然存在；
- **Agent 也可以操作**：定位、聚焦、高亮、预览等动作容易通过 Frontend Tool 表达；
- **变化容易观察**：Agent 的行为会直接反映在共享界面上；
- **容易出现控制权问题**：Agent 操作过程中，用户可能打断、修改或接管；
- **部分交互关系可以跨领域复用**：选择、聚焦、调整、确认、接管并不只属于 GIS。

因此我们利用地图先把这些交互问题看清楚，再判断哪些模式能够迁移到表格、甘特图、工作流、三维场景等其他 GUI。

## 3. 我们怎么验证

### 3.1 基本做法

每次实验只回答一个明确问题，并尽量只改变一种交互方式。

例如验证“Agent 操作界面时是否需要展示当前意图”：

```text
固定：
相同用户任务
相同业务事实
相同 Agent 行为
相同 Tool Call
相同地图最终结果

只改变：
A0：Agent 直接操作地图，最后给结果
A1：Agent 操作地图时，同时给出最小语义反馈
```

然后观察两种方式下是否出现不同的理解、归因、纠偏和困惑。

这里比较的不是两个完全不同的 Demo，而是在尽量相同的条件下改变一个交互设计。

### 3.2 我们关注什么证据

当前阶段不追求复杂指标和人为阈值，重点保留能够解释交互是否成立的实际证据：

- **工程事实**：Agent 实际调用了什么、前端如何执行、最终状态是否一致；
- **实际行为**：使用过程中是否停顿、追问、接管、回退、重复操作；
- **理解情况**：是否知道刚才发生了什么、为什么发生、是谁触发的；
- **反例与失败**：哪里产生误解、状态冲突、错误接管或无法继续。

时间、次数、简单评分可以辅助记录，但当前不把它们当成 KPI。

### 3.3 为什么这种方式具有可信度

我们目前主要通过四点保证验证不是“凭感觉看 Demo”：

**第一，只改变一个核心变量。** 业务事实、Agent 行为和最终结果尽量固定，使观察到的差异更容易归因到交互设计本身。

**第二，实验可以重复。** AGUIMock、固定 fixture 和确定性场景能够让相同输入重复得到相同的基础操作过程，降低大模型随机性对结果的干扰。

**第三，验证真实运行链路。** 不是只看原型图，而是在真实的 `Agent → AG-UI → Frontend Tool → GUI State → Tool Result` 链路上观察交互。

**第四，明确结论边界。** 当前受条件限制，系统的实际体验者只有开发者本人，因此现阶段属于**形成性自测**：用于发现明显问题、保留反例并形成初步判断，不把结果表述成“所有用户都更喜欢/更适合某方案”。后续有真实业务用户条件时，可以使用相同实验重新验证。

## 4. 当前怎么推进

目前已经有地图多步操作的工程基线：Agent 可以通过业务无关的地图意图连续改变同一个 Map Surface，例如：

```text
显示限制图层
→ 聚焦北侧通道
→ 高亮观察点与限制区
→ 预览候选路线
→ 给出最终建议
```

这已经证明“机制可以运行”，但还不能证明“这种交互对用户是合理的”。

因此后续不再以“继续增加地图功能”为主线，而是按交互问题逐步验证。

### 当前第一个实验：EXP-001 Agent 意图可见性

要回答的问题是：

> **Agent 连续改变地图时，仅看到最终结果是否足够？还是需要看到最小的当前意图？**

对照方式：

```text
A0
地图连续变化
→ 最终回答

A1
“正在查看北侧通道”
→ 地图变化
“正在标出重点观察位置”
→ 地图变化
“正在预览候选路线”
→ 地图变化
→ 最终回答
```

当前重点不是证明“A1 一定更好”，而是观察：

- A0 是否真的产生理解和归因问题；
- A1 是否解决这些问题；
- A1 是否反而增加干扰；
- 真正需要改进的是否其实是地图视觉反馈，而不是文字过程提示。

实验结果可能支持当前判断，也可能推翻它。两种结果都能帮助后续设计收敛。

## 5. 最终要形成什么

单个实验不是最终成果。我们希望把多个实验中的稳定发现逐步提升成三个层次。

### 5.1 可复用的交互模式

交互模式描述的是“用户、Agent 和 GUI 之间如何协作”，而不是某个具体地图 API。

例如可能形成：

```text
Agent Action
→ Semantic Feedback
→ GUI Change
→ Continue
```

```text
Agent Suggest
→ Preview
→ User Confirm
→ Execute
```

```text
User Direct Manipulation
→ State Update
→ Agent Re-reason
```

```text
User Interrupt
→ Stop Pending Actions
→ Preserve Confirmed State
→ Resume
```

这些模式只有在实际实验得到支持后，才从“候选模式”升级为推荐模式。

### 5.2 设计原则

多个实验如果反复支持同一种判断，可以进一步形成设计原则。

例如当前待验证的原则包括：

- Agent 改变用户当前工作上下文时，应让用户能够理解变化的意图；
- 用户直接修改共享界面后，Agent 后续行为应基于新的有效状态，而不是继续执行已经过时的计划；
- 低风险、可逆操作可以更多交给 Agent 自动执行，高影响操作应更多采用建议、预览或确认；
- Generative UI 应解决真正不确定的信息表达问题，而不是为了“更 AI”替代所有确定性 UI。

这些目前是**待验证判断**，不是最终结论。

### 5.3 适用边界

任何模式最终都必须同时说明“什么时候适合”和“什么时候不值得使用”。

例如，如果最终验证出“Agent Action → Semantic Feedback → GUI Change”有效，也需要说明：

**可能适合：**

- Agent 连续执行多个可见 UI 操作；
- 操作会改变用户当前工作上下文；
- 用户需要理解过程并可能随时介入。

**可能不需要：**

- 一步即可完成的简单操作；
- 用户只关心最终结果的后台任务；
- 语义反馈会明显打断用户当前工作的场景。

只有同时明确适用边界，交互模式才真正具有复用价值。

---

## 6. 这项工作的价值

最终希望解决的不是“地图里该显示什么提示”，而是给后续真实 Agent 产品提供一组经过实践验证的设计依据。

当团队以后面对地图、表格、甘特图、工作流或其他传统 GUI 时，可以更有依据地回答：

- 什么时候应该让 Agent 直接操作；
- 什么时候应该先建议或预览；
- 什么时候用户直接操作比继续对话更自然；
- 哪些 GUI 状态应该反馈给 Agent；
- Agent 操作过程中需要让用户看到多少信息；
- 用户接管以后，Agent 应该如何继续；
- 哪些场景固定 UI / 受控组件已经足够，哪些场景才值得使用 Generative UI。

因此整个验证过程可以概括为：

```text
实际交互问题
↓
地图实验
↓
可复核的观察与反例
↓
Interaction Pattern
↓
Design Principle
↓
适用边界
↓
指导真实 Agent + GUI 产品设计
```
