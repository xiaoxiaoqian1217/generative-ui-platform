# Agent–User Interaction 地图场景验证研究设计

> **文档性质：Research Protocol（研究协议 / 验证研究设计）**  
> **版本：v0.2**  
> **日期：2026-08-24**  
> **适用项目：generative-ui-platform / dev_1.0**

## 一句话定位

**以地图作为实验场，通过可证伪假设、受控实验和用户证据，回答 Agent 与用户应该如何共同使用一个有状态 GUI；代码 Demo 是实验装置，最终成果是可复用的交互模式、设计原则与适用边界。**

---

## 0. 这份文档解决什么问题

当前项目已经能持续产出 Demo、Issue、E2E 和协议验证，但如果缺少上位研究设计，容易出现三个问题：

1. **功能完成被误认为结论成立。** Tool Call 跑通只能证明“系统能做到”，不能证明“用户能理解、愿意使用、控制感更好”。
2. **不同 Demo 之间缺少共同问题。** 每个功能都能单独成立，但很难回答“这些实验共同告诉我们什么”。
3. **结论容易被当前实现绑定。** 例如 MapLibre、CopilotKit、AG-UI、某个业务 Agent 都可能变化，而我们真正需要沉淀的是跨实现的 Agent–User Interaction 知识。

因此，这份文档不是 PRD、架构设计、接口规范或开发计划，而是它们之前的“研究约束”：**先定义要回答的问题、假设、证据和判据，再决定需要做什么 Demo。**

## 1. 研究目标与边界

### 1.1 研究目标

本项目的核心目标不是“做一个地图 Agent”，而是：

> **研究在传统有状态 GUI 中，Agent 与用户如何分工、共享上下文、让渡控制权，并形成可理解、可纠偏、可恢复的协作闭环。**

地图是首个实验域，因为它同时具备：

- 强状态性：视口、图层、选区、路径、高亮都持续存在；
- 强直接操纵：点击、拖拽、框选、调整路线天然适合用户介入；
- 强可见反馈：Agent 的每次动作都能即时观察；
- 多步任务：适合验证 Agent 连续行动、等待、打断、恢复；
- 易与业务解耦：`focusOn`、`highlight`、`previewPath` 等可表达地图域意图，而不必暴露具体业务实体；
- 当前已有工程基线：项目已经跑通 AG-UI → Frontend Tool → MapLibre 的确定性链路，可以把精力转向交互问题本身。

### 1.2 核心概念：什么是“有状态 GUI”

本文所说的 GUI，指前端可交互界面，例如地图、侧边栏、卡片、表格、图层、路径、筛选器和按钮等。

本文特别强调 **有状态 GUI（stateful GUI）**，因为研究重点并不是“Agent 能否调用某个前端能力”，而是：

> **用户与 Agent 如何共同操作一个会持续保留上下文和变化的界面。**

以地图为例，Agent 与用户的操作会持续改变并保留界面状态，包括：

- 当前视口；
- 当前显示图层；
- 当前高亮与选择对象；
- 当前预览路线；
- 用户最近一次直接操作；
- 哪些状态由 Agent 产生；
- 哪些状态由用户确认、修改或覆盖。

因此，地图不是一次性渲染结果，而是一个持续演化的**共享交互表面（shared interactive surface）**。用户与 Agent 都可能成为这个表面的操作者。

这会产生普通聊天中不明显、但本研究必须回答的问题：

- Agent 修改界面后，用户再次修改时谁拥有最终控制权？
- 用户正在直接操作时，Agent 是否可以继续改变同一状态？
- 哪些用户操作需要反馈给 Agent，哪些只是本地浏览状态？
- 用户纠偏后，Agent 尚未执行的旧计划是否应该继续？
- 新一轮推理应该基于初始状态，还是当前 GUI 的真实状态？
- 哪些状态属于临时预览，哪些属于已经确认的稳定状态？

因此，“有状态”不是对 GUI 的修饰性描述，而是在限定本研究的问题空间：

> **当人与 Agent 同时成为一个持续存在的软件界面的操作者时，控制权、状态归属、反馈、打断与恢复规则应该如何设计。**

### 1.3 不研究什么

首轮研究明确不把以下问题混入同一实验：

- 业务推理是否正确；
- 路径规划算法是否优秀；
- 大模型是否能自主发现所有工具；
- 地图渲染性能与 GIS 算法质量；
- Runtime Platform、持久化、复杂多 Agent 编排；
- “生成式 UI 越多越先进”之类预设结论。

这些因素可以在后续研究，但首轮要尽量固定，否则交互失败时无法归因。

## 2. 研究方法：DSRM + Research Question / Hypothesis + Evidence-driven Evaluation

本项目采用三层方法组合，而不是单一“做 Demo 看感觉”。

### 2.1 上层：Design Science Research Methodology（DSRM）

DSRM 适用于“通过构造并评估技术人工物来获得问题与解决方案知识”的研究。项目按六步循环：

1. **问题识别与动机**：传统 Chat + GUI 中，人和 Agent 的协作边界不清晰。
2. **定义解决目标**：交互应可理解、可预期、可控、可纠偏、可恢复，并尽量能跨业务迁移。
3. **设计与开发**：实现受控 Demo、地图工具面、交互反馈和实验变体。
4. **演示**：在固定母场景中运行真实任务流程。
5. **评估**：采集工程事实、用户行为、用户表述、异常与反例等可追溯证据，检验假设。
6. **沟通与沉淀**：输出交互模式、决策矩阵、适用边界与最终验证报告。

**关键点：设计与开发只是第 3 步，不是研究终点。**

### 2.2 中层：Research Question → Hypothesis → Experiment → Evidence

当前阶段以探索性、形成性验证为主，不强行要求每个问题都转化为量化指标。每一个实验按以下链条定义：

```text
Research Question（要回答什么）
  ↓
Hypothesis（当前可被推翻的判断）
  ↓
Experiment（如何控制变量进行验证）
  ↓
Evidence（需要观察和保存什么事实）
  ↓
Interpretation（这些证据意味着什么）
  ↓
Conclusion / Boundary（结论与适用边界）
```

例如：

```text
RQ4：Agent 的意图和动作需要多大程度可见？
  ↓
H4：多步操作至少需要“当前意图 + 关键结果”的最小语义反馈
  ↓
Experiment：固定 Tool Call、业务事实和地图终态，只比较 A0 / A1
  ↓
Evidence：用户能否复述发生了什么、能否解释原因、是否误判发起者、何时出现困惑、是否主动追问
```

本阶段追求的是：**结论有证据、证据可追溯、反例不被忽略**，而不是为了显得科学而人为设置“理解率 ≥ 80%”之类缺少依据的阈值。

### 2.3 底层：可证伪假设 + 混合证据

对每个 Research Question 写出可证伪假设，并优先采集四类证据：

- **工程证据**：Tool Call、Result、Run、地图终态、失败/恢复事件，回答“系统实际上发生了什么”；
- **行为证据**：用户点击、等待、打断、接管、回退、重新询问等，回答“用户实际上做了什么”；
- **认知证据**：任务后复述、访谈、回放解释，回答“用户认为发生了什么”；
- **反例证据**：困惑、误解、错误接管、状态冲突、无法恢复等，回答“设计在什么条件下失败”。

任务耗时、操作次数、评分等量化数据仍然可以记录，但在首轮形成性研究中只作为**辅助证据**，不默认作为硬通过标准。

工程证据证明“机制成立”，用户证据才能支持“交互成立”。两者不得互相替代。

## 3. 核心 Research Questions

首轮建议固定 7 个上位问题。后续所有地图 Demo 必须至少服务其中一个问题。

### RQ1：什么时候应该用自然语言，什么时候应该直接操作 UI？

研究语言表达与 Direct Manipulation 的边界。例如“扩大东侧区域一点”究竟更适合继续对话，还是用户直接框选/拖动更自然。

### RQ2：Agent 应该控制 UI 到什么程度？

研究自动执行、建议、预览、等待确认之间的控制权边界。不同风险、可逆性和影响范围的动作是否应采用不同策略。

### RQ3：用户操作 UI 后，哪些状态必须反馈给 Agent？

研究 GUI 状态如何进入 Agent 上下文。不是所有鼠标移动都值得同步，但改变任务语义的选择、范围、路线调整通常需要被 Agent 理解。

### RQ4：Agent 的意图和动作需要多大程度可见？

研究 A0“只看终态”、A1“最小语义反馈”、A2“持久过程视图”之间的价值。目标不是展示更多日志，而是找到足够支撑归因和预测的最小反馈量。

### RQ5：用户如何打断、纠偏、接管，再把控制权交还给 Agent？

研究 Interrupt、Cancel、Supersede、Resume 以及手动接管后的语义，特别是哪些状态保留、哪些后续 Agent 行动应失效。

### RQ6：Fixed UI / 受控组件 / A2UI / Generative UI 的真实适用边界是什么？

把当前工程路线当作“待验证假设”，而不是先验结论。重点验证：确定性操作是否更适合受控 UI；未知信息结构是否才需要动态生成；生成 UI 是否真的提高任务表现或只增加复杂度。

### RQ7：地图中验证出的哪些交互模式可以迁移到其他业务系统？

检验模式是否能脱离 GIS 词汇描述。例如：

```text
Agent 建议 → UI 展示候选 → 用户直接修改 → 结构化状态回传 → Agent 重新推理
```

如果它可以映射到表格筛选、工作流编辑、甘特图调整或三维场景，它才具备真正的泛化价值。

## 4. 初始可证伪假设

以下是假设，不是结论。实验结果允许推翻它们。

| 编号 | 假设 | 主要对应 RQ | 可反驳的证据 |
| --- | --- | --- | --- |
| H1 | 对复杂空间范围和连续微调，直接操纵 UI 比纯自然语言更高效、更少歧义 | RQ1 | 用户使用 UI 反而更慢、纠错更多或更难理解 |
| H2 | 低风险、可逆的视觉操作可由 Agent 直接执行；高影响或不可逆操作应采用预览/确认 | RQ2 | 用户对自动执行同样信任，或确认步骤显著妨碍任务且不降低错误 |
| H3 | 改变任务语义的 UI 操作需要转成结构化状态回传 Agent；纯视觉浏览不必全部同步 | RQ3 | 不同步仍能稳定完成任务，或全量同步没有带来噪声/成本问题 |
| H4 | 多步 Agent 操作至少需要“当前意图 + 关键结果”的最小语义反馈；只看终态容易失去归因 | RQ4 | A0 与 A1 在理解、追问、控制感上没有有意义差异 |
| H5 | 用户纠偏后，未执行的旧计划应被明确 supersede；已经确认的稳定状态应尽量保留 | RQ5 | 用户更偏好完全回滚，或旧计划继续执行不会造成理解/控制问题 |
| H6 | 确定性操作默认使用受控 UI；Generative UI 的主要价值在未知或高度可变的信息表达，而不是任意操作界面 | RQ6 | 动态生成在确定性操作中显著提升效率/理解且不损害可靠性 |
| H7 | 可泛化交互模式必须能在不使用 GIS/业务名词的情况下完整描述其状态和角色关系 | RQ7 | 去掉领域词汇后模式失去关键语义，无法迁移到第二个领域 |

## 5. 实验设计原则

### 5.1 一次只改变一个核心变量

如果比较 A0 / A1 / A2，必须固定：

- Agent 输入；
- Tool Call 顺序；
- fixture 业务事实；
- 地图终态；
- 任务目标；
- 失败注入条件。

只改变“用户看见什么过程反馈”。这样差异才能归因到交互设计，而不是业务结果不同。

### 5.2 首轮固定业务事实，隔离业务智能

延续现有“北侧通道巡逻方案研判与调整”母场景：候选路线、观察点、限制区等均由 fixture 提供。Agent 首轮只决定地图意图和交互节奏，不负责生成专业业务事实。

这样做的目的不是弱化业务，而是控制混杂变量：如果同时让 Agent 做路线规划、威胁分析和 UI 操作，失败时无法判断究竟是哪一层出了问题。

### 5.3 先形成性验证，再考虑统计性结论

早期目标是发现问题和修正交互，不追求“统计显著”。可以先使用内部目标用户、业务同事或接近目标角色的参与者做形成性测试。

如果未来需要对外声称“方案 A 普遍优于方案 B”，再单独设计更严格的样本、随机化/平衡顺序和统计分析。**当前阶段禁止用少量体验样本包装成普遍结论。**

### 5.4 对照设计优先于“做完以后问好不好”

优先使用同任务对照：

- A0：终态 + Assistant 文本；
- A1：最小语义反馈；
- A2：持久过程视图（仅当 A1 仍不能解决问题时）；
- 语言纠偏 vs 直接操纵；
- 自动执行 vs 预览确认；
- 中断后全回滚 vs 保留已确认状态。

### 5.5 避免取证方式污染观察

实时 Think-Aloud 可能改变用户原本的操作节奏和决策。首轮可优先采用屏幕/事件记录 + 任务后回放解释（Retrospective Think-Aloud），必要时再补充量化记录。重点是保留可复核证据，而不是为了采集数字改变用户行为。

## 6. 证据体系

### 6.1 四类核心证据

| 类型 | 示例 | 主要回答什么 |
| --- | --- | --- |
| 工程证据 | Tool Call/Result、状态变化、错误、恢复、地图终态 | 系统实际上发生了什么 |
| 行为证据 | 点击、等待、打断、接管、回退、重新询问 | 用户实际上做了什么 |
| 认知证据 | 任务后复述、访谈、回放解释 | 用户认为发生了什么 |
| 反例证据 | 困惑、误解、状态冲突、错误接管、无法恢复 | 设计在什么条件下失败 |

四类证据应尽可能相互印证。例如，用户说“我不知道地图为什么跳过去了”时，应能回到对应 Tool Call、界面反馈和用户后续操作，形成完整证据链。

### 6.2 首轮优先观察什么

**理解与归因**

- 用户能否说出 Agent 刚刚做了什么；
- 能否说出为什么发生变化；
- 能否区分 Agent 操作与自己的操作；
- 哪一步开始出现困惑或错误归因。

**控制与纠偏**

- 用户需要停止或修改时是否知道怎么做；
- 用户接管后 Agent 是否继续执行过期计划；
- 用户是否能恢复到可接受状态；
- 哪些状态保留或清理与用户预期不一致。

**状态闭环**

- Tool Result 是否与视觉终态一致；
- Agent 上下文是否与用户实际选择一致；
- Cancel / Supersede 后是否仍出现过期操作；
- 用户直接操作改变任务语义后，Agent 是否正确接续。

**主动行为与反例**

- 用户是否主动追问“你刚才做了什么/为什么”；
- 是否主动寻找更多过程信息；
- 是否重复操作、回退或尝试绕过当前交互；
- 出现了哪些预先没有想到的失败方式。

### 6.3 可选量化记录

在不干扰实验的前提下，可以记录以下数据辅助解释现象：

- 任务完成时间；
- 对话轮次；
- UI 操作次数；
- 追问、纠偏、撤销、取消次数；
- 任务是否完成；
- 简单的理解或控制感评分。

这些数据当前**不是 KPI，也不默认设置通过阈值**。只有在后续需要比较稳定方案、扩大样本或形成更强外部结论时，才进一步定义主要指标、样本设计和统计方法。

### 6.4 证据使用纪律

1. 每条结论必须能追溯到具体 Research Question、Experiment 和原始证据。
2. 实验前写明“什么现象支持假设、什么现象反驳假设”，避免事后只挑有利观察。
3. 反例与失败案例必须保留，不能因为主路径跑通而忽略。
4. 工程测试通过不能替代用户证据。
5. 单个用户的一句主观评价不能直接提升为普遍结论，应结合行为与其他证据解释。
6. 量化记录是辅助证据；没有足够研究设计时，不使用人为阈值制造伪精确。

## 7. 证据等级：避免把 Demo 当成验证结论

建议给每项结论标注 Evidence Level：

| 等级 | 含义 | 可以声称什么 |
| --- | --- | --- |
| E0 概念 | 只有设计/讨论 | “这是一个待验证设想” |
| E1 工程证据 | 确定性链路、测试、E2E 可重复 | “机制可以实现并稳定运行” |
| E2 形成性用户证据 | 目标用户/接近目标角色实际使用并观察 | “发现了明确体验问题/倾向” |
| E3 对照证据 | 同任务多方案对照、控制变量 | “在当前任务与样本下，方案 X 表现更好/更差” |
| E4 迁移证据 | 第二领域/第二业务系统复验 | “该模式具有初步跨域泛化证据” |

**当前场景 A 的多步 Tool Call 基线主要属于 E1。** 它是后续用户实验的必要前提，但不应直接升级成“用户理解良好”或“这种交互模式有效”的结论。

## 8. 地图实验主线

保留当前 A-D / E-H 的场景分解，但重新赋予“它在回答哪个 Research Question”的含义。

| 场景/维度 | 核心问题 | 主要 RQ | 优先证据 |
| --- | --- | --- | --- |
| A 多步工具中介 | 连续 Agent 操作是否可理解、可归因 | RQ4 | A0/A1 对照、理解与追问 |
| B 征询等待 | Agent 何时应停止并把决策交给用户 | RQ2 | 决策正确性、等待理解、控制感 |
| C 打断纠偏 | 用户语言修改目标后旧计划如何失效 | RQ5 | supersede、恢复、状态残余 |
| D 混合主导 | 用户直接改地图后 Agent 如何接续 | RQ1/RQ3/RQ5 | 操作效率、状态回传、重推理 |
| E 失败路径 | 错误发生后用户能否理解和恢复 | RQ5 | 恢复成功率、错误归因 |
| F 意图可见性 | 用户是否知道谁做了什么、为什么 | RQ4 | 归因、预测、追问 |
| G 状态残余 | 哪些临时/确认状态应保留 | RQ3/RQ5 | 状态一致性、用户预期 |
| H 恢复接续 | 新旧 Run 如何衔接 | RQ5 | 过期动作、恢复正确性 |

## 9. 每个 Demo 开发前必须先写 Experiment Card

后续 Issue 不再只写“实现什么”，至少先填以下内容：

### Experiment Card 模板

**Experiment ID**：EXP-XXX  
**Research Question**：RQ?  
**Hypothesis**：H?  
**Goal**：本实验要理解什么？  
**Changed Variable**：本次只改变什么？  
**Controlled Variables**：哪些输入、业务事实、地图终态必须固定？

## 10. 与当前 generative-ui-platform 的关系

### 10.1 当前已经具备的研究资产

当前 `dev_1.0` 已经提供很好的实验基础：

- `AGUIMock → AG-UI → CopilotKit useFrontendTool → MapLibre → Tool Result` 已跑通；
- Issue #214 已建立业务无关地图域意图：`setLayerVisibility`、`focusOn`、`highlight`、`previewPath`；
- 同一个持久 Map Surface 可消费多步 Agent 操作；
- Inspect / E2E 已能采集调用顺序、结果关联和地图终态；
- `MAP-AGENT-INTERACTION-VALIDATION.md` 已经形成 A-D 核心场景、E-H 横切维度和 A0-A2 呈现变体。

这些不需要推翻，它们应被重新定位为：**Research Protocol 下面的实验装置、场景设计与工程证据。**

### 10.2 当前最需要修正的工作方式

当前 README 中“确定性交互使用 Frontend Tool / Controlled UI；不确定业务结果展示逐步进入 A2UI / Generative UI”是一个很合理的工程策略，但从研究角度应把它写成 **RQ6/H6 的当前工作假设**，继续用实验验证它的适用边界，而不是把它提前当成最终结论。

同样，场景 A 当前已经证明“Agent 能连续操作共享地图”，但还没有证明：

- 用户能否理解这些连续操作；
- 用户是否需要过程反馈；
- 何时应该停下征询；
- 用户纠偏后旧计划应该如何处理；
- 用户直接修改地图是否比语言更自然；
- 这些模式能否迁移到第二种 GUI。

这正是下一阶段研究的主体。

## 11. 最终要沉淀的成果

项目最终不以“完成多少地图功能”衡量，而以能否形成以下知识资产衡量。

### 11.1 Agent–User Interaction Pattern Catalog

例如：

- Suggest → Preview → Confirm → Execute；
- Agent Action → Semantic Feedback → Continue；
- User Direct Manipulation → State Commit → Agent Re-reason；
- Interrupt → Supersede Pending Plan → Preserve Confirmed State → Resume；
- Agent Yield → User Decision → Agent Continue。

每个 Pattern 都要记录：适用条件、角色、状态变化、失败路径、UI 约束、证据等级和已验证场景。

### 11.2 Interaction Decision Matrix

回答团队最需要的选型问题：

- 什么情况只需要自然语言；
- 什么情况应该使用 Direct Manipulation；
- 什么情况 Agent 可以自动执行；
- 什么情况必须预览/确认；
- 什么情况固定 UI / 受控组件足够；
- 什么情况值得使用 A2UI / Generative UI。

### 11.3 设计原则

例如最终可能形成（需实验验证）：

- 高影响操作优先“建议/预览/确认”，低风险视觉操作允许直接执行；
- 多步 UI 变化必须提供足够的意图可见性，而不是暴露底层 Tool Log；
- 用户改变任务语义时应优先以结构化状态反馈 Agent；
- 用户接管后，旧计划未执行部分默认失效；
- Generative UI 的价值由任务不确定性决定，而不是由“是否用了 AI”决定。

### 11.4 阶段验证报告

最终报告采用固定结构：

```text
研究问题
  ↓
假设
  ↓
实验设计
  ↓
证据
  ↓
支持 / 部分支持 / 推翻
  ↓
适用边界
  ↓
形成的 Interaction Pattern / Design Principle
  ↓
下一轮问题
```

这样即使某项假设被推翻，仍然是有效研究成果，而不是“Demo 失败”。

## 12. 从现在开始的执行顺序

### Step 1：冻结上位问题

先采用本文 RQ1–RQ7，不继续新增功能目标。新的想法先归类到某个 RQ；归不进去的先进入 backlog。

### Step 2：把现有成果重新标注证据等级

- locateDevice：E1 单步工程基线；
- 场景 A 多步地图操作：E1 多步工程基线；
- A0：当前体验 baseline，不得称为推荐方案。

### Step 3：下一项优先做 EXP-001：A0 vs A1 意图可见性

这是当前最自然的第一个“真正用户交互实验”，因为实现成本最低、变量最清晰，并且直接回答 RQ4/H4。

实验只改变反馈方式，不改变 Tool Call 与地图终态。先观察：

- 用户能否说明每一步是谁发起、为什么发生；
- 是否需要追问 Agent；
- 是否能够预测接下来会发生什么；
- A1 是否提高理解，而没有增加明显认知负担。

只有 A1 仍不足时，再投入 A2 持久过程视图。

### Step 4：进入 B → C → D

- B 回答“何时征询/等待”；
- C 回答“语言打断后如何失效旧计划”；
- D 回答“用户直接操纵 + Agent 重新推理”。

D 很可能是地图域最有价值的实验，因为它直接触及 Chat 与 GUI 融合的核心：**用户不需要把一切重新描述成语言。**

### Step 5：至少做一次跨域迁移

在地图中得到稳定 Pattern 后，不立即建设“通用交互平台”，而是选择一个第二 GUI 做最小迁移验证，例如：

- 表格筛选/选择；
- 工作流节点调整；
- 甘特图计划调整。

如果模式不改结构就能复用，才提升到 E4，并考虑正式抽象公共能力。

## 13. 研究纪律 / Stop Rules

为了避免项目重新演化成“大平台”，约定以下停止规则：

1. **没有 Research Question，不开发实验功能。**
2. **没有对照或可证伪假设，不把 Demo 称为验证。**
3. **E1 工程证据不能推出用户体验结论。**
4. **只有一个领域的成功不能宣称泛化。**
5. **框架已有能力优先复用，不为了研究模式提前造 Runtime Platform。**
6. **每次只新增满足当前实验的最小实现。**
7. **当新功能不能改变任何研究结论时，应停止投入。**
