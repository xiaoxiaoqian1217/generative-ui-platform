# Agent 交互泛化方向讨论记录

- **性质：** 非规范性讨论记录（research）
- **日期：** 2026-08-19
- **背景：** 与领导沟通"现阶段应该泛化什么"后，结合当前仓库现状的第一性原理推演

## 起点观点

来自领导的方向判断：

- 现阶段应该泛化的是 Agent 的交互方式，而不是 UI 界面。
- 第一阶段做受控组件，这是最现实的路径。
- 交互泛化不应绑定业务语义。

本文记录对这三个观点的推演过程与结论，以及它们与当前架构现状的对照。

## 第一性原理：交互的本质

用户与 Agent 的交互本质是有方向、有生命周期的事件交换。

交互方式属于对话层：谁发起、谁等待、传什么、生命周期如何。
UI 界面属于呈现层：交互在某一端的呈现细节。
同一个交互方式可以用不同 UI 承载，同一"征询"可以渲染成按钮组、表单或纯文本等待输入。
因此泛化交互方式不需要以泛化 UI 为前提。

关键推论：交互动作是有限集，UI 形态是无限集。
人与 Agent 协作的基本动作收敛为少数几类，不随业务增多。
UI 随业务、品牌、审美发散，每个产品都想要不一样。

两条轴的变化方向相反，决定了工程策略相反：

| 轴 | 变化方向 | 工程策略 |
| --- | --- | --- |
| 交互方式 | 收敛：有限、协议化、不随业务变 | 泛化（一次投入，长期复用） |
| UI 呈现 | 发散：随业务、品牌、审美无限变 | 固化（压成有限集合） |

泛化有限集是协议问题，可测可控。
泛化无限集是生成问题，需要 Compiler / Presentation Pipeline。
后者属于已删除并明确 out of scope 的架构。
因此"泛化交互方式而非 UI"不是偏好，是当前约束下唯一成立的泛化路径。

## 业务无关的交互模式词汇

从第一性原理归纳，用户与 Agent 的交互可收敛为五类，均不含业务名词：

| 交互模式 | 本质 | 现状对应 |
| --- | --- | --- |
| 单轮问答 | text in / streaming text out | 已有 |
| 委托执行 | 给任务、看进度、收结果 | Activity / Artifact，Issue #200 验证中 |
| 征询等待 | Agent 停下问，用户答，Agent 恢复 | 缺口，对应 SACS Interrupt / Resume |
| 工具中介行动 | Agent 驱动前端能力，用户观察结果 | locateDevice 已跑通 |
| 打断纠偏 | 用户中断 Agent 当前 Run | 协议已定义，闭环语义未实现 |

"不绑定业务语义"的准入测试：一个交互模式必须能在不使用任何领域名词（设备、告警、任务）的情况下被完整描述。
业务语义只允许出现在交互内容（payload）中，永远不进入模式结构。
"从 N 个选项中选择一个"是模式，"选择一台设备"是内容。

这与现有 Catalog 纪律一致：`metric.ts` 的设计注释明确写道 "Domain fields such as `droneCount` are intentionally absent"。

## 三层模型

```text
Layer 3  呈现端点   受控组件（Catalog / A2UI Renderer）                固化
Layer 2  交互模式   事件之上的对话编排闭环                             泛化，交付物
Layer 1  事件词汇   AG-UI 协议（TEXT_MESSAGE / TOOL_CALL / RUN_*）    不动
```

AG-UI 形式化的是事件词汇，不是对话结构。
一个交互方式不是单个事件，是事件之上的编排。
协议提供词汇，模式是词汇的用法。

以 locateDevice 为例：

- AG-UI 只定义了 TOOL_CALL_* 事件与 TOOL_CALL_RESULT 回传。
- Agent 发起调用、Workbench 挂起、MapLibre 执行、结果回传、Agent 继续，这个闭环的全部语义（挂起期间算什么状态、失败如何处理、用户可否取消、超时怎么办）都不在协议里。
- 这个闭环是使用协议的方式，由 Workbench 侧通过 `useFrontendTool` 自行搭建。

因此 AG-UI 之上仍然存在真实的泛化空间，即 Layer 2：

1. 模式的状态机语义：挂起、取消、超时、失败、恢复。
2. 能力契约与降级：每种交互模式声明所需能力，Agent 侧声明支持范围，缺口显式呈现并走确定降级路径，不伪造能力。
3. 跨 Agent 同构：同一模式无论底层是 AGUIMock 还是 SACS，对用户表现一致，在 Workbench 只实现一次。

## Layer 2 的试金石

SACS 当前不支持 client-provided Frontend Tools，但这是当下能力状态，不是永久属性。

Layer 2 做对了的验收标准：SACS 将来支持 Frontend Tools 那天，改动应只发生在能力声明与接入配置，Workbench 中交互模式的实现零改动。

这是"考虑更长远"在工程上的具体化：把产品交互语义与某个 Agent 的当下能力解耦。

## 固化呈现端点的理由

1. 安全边界：仓库规则禁止执行模型生成的任意 HTML / JavaScript，渲染只能从受控闭集中选择。
2. 可靠性：有限集合意味着每个交互状态都有已知、可 e2e 回归的呈现。
3. 职责分离：Agent 智能用于选择交互模式与填充内容，不用于画界面；UI 的发散性被引导到内容层与 Theme 层。

Theme Tokens 后置的决策在此找到结构性理由：Theme 是承接 UI 发散性的正确阀门，不是泛化轴。

固化不等于不变：闭集可以增长（新增受控组件），新交互模式可以补呈现端点。
变化被限制在内容层与主题层，永远不进入生成渲染层。

## 对当前 roadmap 的修正含义

1. Issue #200（真实 SACS 互操作）的地位上升。
   它不只是 A2UI 的配角，而是泛化交互方式的主战场：streaming、lifecycle、interrupt / resume、state、artifact 的端到端验证，就是把每种交互模式跑成可复用闭环的过程。
2. Catalog / A2UI / 受控组件重定位为呈现端点。
   它们服务交互，不承担泛化轴。
   Metric / StatusBadge / InfoRow 全部服务于"陈述"类交互，这是呈现端的现状，不需要为泛化而扩张。
3. 下一个增量是把"征询等待"闭环跑通。
   它对应 SACS Interrupt / Resume，呈现用什么 UI 是后置的、可替换的。
   不必急于为它新增 Catalog 条目。
   这是本次讨论修正掉的一个早先观点：不要把交互方式和承载它的 UI 绑死。
4. Layer 2 的一部分 CopilotKit 已提供（`useFrontendTool`、human-in-the-loop 机制）。
   泛化动作是清点：框架已有的直接复用，没有的（如 interrupt / resume 的状态机语义）在 Issue #200 的真实场景里补。
5. 薄 Layer 2 警告。
   Layer 2 交付的是一组命名闭环加能力契约，载体是 Workbench 与薄 Runtime，复用 AG-UI / CopilotKit 已有机制。
   它长成"交互框架 / 交互平台"的那一刻，就撞上 Feature admission gate 与被删除架构（presentation-contract 等）的边界。

## 与当前架构的相容性

本方向与 ADR-0029 / ADR-0030 的现有架构不冲突，是对同一条路的更准确命名：

- 薄 Runtime + AG-UI 原生契约的边界不变。
- 受控渲染与 Catalog 的 business-agnostic 纪律不变。
- SACS capability gap 显式呈现的纪律不变，且升级为 Layer 2 能力契约的一部分。
- 变化只发生在视角：泛化轴从 UI 组件上移到交互模式，Catalog 从"泛化对象"重定位为"呈现端点"。
