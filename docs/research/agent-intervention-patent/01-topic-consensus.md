# 选题演进与阶段共识报告

日期：2026-09-29。性质：头脑风暴阶段归档，非规范性研究输入。

本文保存选题依据与讨论边界；技术方案、专利证据、创新深化及文献计划分别见本目录 02—05。它不是专利授权结论，也不代表仓库已经实现候选机制。

## 1. 当前方向

研究核心是：**Agent 请求协助，或用户在 Agent 执行过程中主动参与时，系统如何承接其目的，让用户知道该看什么、能改什么，以及操作后会发生什么。**

两种发起方式地位相同。用户可在任务正常运行时补充要求、纠正理解、调整目标或追加检查，无须等待告警或 Agent 邀请；是否暂停、是否改变计划，由具体操作决定。

保留两个候选题目，暂不确定唯一标题：

1. 一种面向智能体长时任务的协同介入交互动态组织方法及系统。
2. 一种基于任务情境与介入目的的智能体协同交互动态组织方法及系统。

当前更适合用第二个作为工作标题：它直接表达交互组织的依据，不要求首个原型就证明数小时长时任务的效果。若后续确实验证了多次介入、离开后返回及累积状态变化，再评估第一个标题。

这里的“动态”指随协同需求组织信息和操作能力；可以由规则、组件和结构化数据实现，不要求 LLM 实时生成页面代码。

2026-09-29 后续确认：**优先围绕地图交互，以无人巡检为主应用场景**。后续如需验证迁移性，优先选择另一个地图业务，不要求先做纯数据分析场景。用户随后否定围挡绕行作为人工介入主需求。现已撤回该设定；依据论文与专利推荐“疑点复核与定向补检”，仍为待业务验证的候选，具体行业尚未确认。见 [06 场景说明](06-patrol-scenario.md)与 [07 需求证据](07-real-inspection-needs.md)。

## 2. 选题怎样收敛

以下是对本次讨论的主题归纳，不把未完整保留的早期讨论补写成确定事实。

| 阶段 | 当时关注 | 收敛原因 | 保留下来的价值 |
| --- | --- | --- | --- |
| 从智能交互发散 | 方案解释、空间证据、介入时机与窗口 | 单个展示功能难以表达完整人机协同；也容易过度依赖地图业务 | 解释依据和时机作为交互输入 |
| 任务情境驱动界面 | 随任务状态展示不同组件 | 动态 UI、上下文界面并非空白，仅换组件不足以支撑发明点 | 确立“交互随任务变化” |
| 明确介入对象 | 参数、计划、条件、控制等分别组织交互 | 统一确认框表达能力不足，完整控制台又可能使修改范围不清楚 | 从“是否找人”深入到“找人做什么” |
| 引入临时作用域 | 本次允许改哪些对象、属性和动作 | 必须避免用户误以为可改全局任务，也不能让前端自行扩大允许范围 | 让操作边界可见、可校验 |
| 绑定任务状态与生命周期 | 旧界面能否继续提交、重复提交如何处理 | 长过程中的任务变化会使旧选择失去适用性 | 让用户操作对应当前真实任务 |
| 关注回写和继续 | 改动影响什么、保留什么、从哪里继续 | 只生成界面还没有完成协作闭环；但不能假设所有 Agent 支持局部恢复 | 把修改结果和后续行为反馈给用户 |

这不是从交互转向通用状态管理。作用域、状态绑定和恢复机制都应回答具体交互问题：**用户是否看得懂操作边界，操作能否按预期生效，系统是否说明了实际影响。**

| 级别 | 内容 | 后续处理 |
| --- | --- | --- |
| 已认可方向 | 以人与 Agent 的智能交互为核心 | 作为选题约束 |
| 已认可方向 | 面向运行中的任务，同时支持 Agent 请求参与与用户主动参与，覆盖补充、选择、修改与控制 | 分别验证两种入口，包括任务正常时主动调整 |

| 已认可方向 | 保留用户看得见、能操作的介入界面 | 每个技术机制必须对应可观察交互 |
| 候选机制 | 从协同需求计算临时可修改范围 | 明确输入、规则与拒绝条件 |
| 候选机制 | 界面绑定目标对象和相关状态前置条件 | 验证过期、并发及无关变化 |
| 候选机制 | 结构化局部回写、依赖失效和受约束恢复 | 验证执行器能力与失败降级 |
| 候选机制 | 最小充分信息与操作集合 | 用覆盖规则与用户任务验证，不以按钮少为准 |
| 待确认 | 哪些信息对完成本次介入确实必需 | 任务分析、专家走查和形成性研究 |
| 待确认 | 与公开专利及非专利资料的可辩护差异 | 逐项检索、组合分析与技术交底审查 |
| 待确认 | 是否应把“长时”写进题目 | 取决于实验覆盖，不提前承诺 |
| 待确认 | 产品是否准入候选恢复/生命周期机制 | 另按仓库工程准入流程决定 |

“已认可”只表示本次选题讨论的方向共识，不等于需求被业务人员验证，也不等于用户确认了本文提出的全部字段、算法和工期。

## 4. 暂不作为单独主创新的内容

不再单靠以下表述证明创新：动态生成 UI、普通人工审批、用户修改 Agent 计划、根据上下文改变展示、状态版本号、暂停后继续、减少按钮。

它们可以是方案必要组成部分，但要继续回答：与既有机制相比，**在什么条件下，通过什么具体处理，产生了什么可验证的差异**。一篇资料没有完整覆盖所有步骤，不足以排除其他资料的组合压力。证据与不确定性集中维护在[专利对比报告](03-patent-comparison.md)。

## 6. 首批实施例与成功标准

先验证人的增量信息、运行中介入必要性与空间操作需求，再冻结两张候选任务卡：

1. **M1 疑点证据复核**：围绕资产及构件的证据判断尚缺什么，允许修正关联、补充有来源的信息或保留待核验。
2. **M2 追加专项检查与任务影响确认**：专家提出检查目标或范围，系统转为可执行采集任务；仅真实业务冲突才需要额外取舍。

两张任务卡按需覆盖“选资产或构件、核对证据、指定补检目标”。自主避障和规则明确的补拍不打扰用户；结束后审核即可解决的事项不强制实时介入。选点与既有区域选择先行，自由绘制区域等较复杂操作按需要加入；地图从首版参与，但不额外承担自动路径规划研究。原参数修改示例保留为技术解释，不再用“没有搜索结果所以改半径”代替主业务需求。

成功不是“界面生成了”或“事件流跑通了”。至少要分别获得：

- 交互证据：用户能判断本次需要做什么、能改哪里、提交后会发生什么。
- 系统证据：过期和越界操作被拒绝，合法修改准确生效，恢复与回退行为可追踪。
- 研究证据：明确哪些情形有收益、哪些情形无收益或更差，保留失败记录。

当前没有实验数据。具体任务、记录格式与推进顺序见[文献计划](05-literature-plan.md)。
