# 需求推导与民用应用场景设计

> 日期：2026-09-29｜性质：研究输入与候选设计，非业务确认、非实现规范、非专利法律结论。
>
> 本文从专利的核心技术问题反推需求条件，再基于需求设计应用场景。所有场景均为候选，须先通过 [07](07-real-inspection-needs.md) 的取证与访谈检验。军事候选场景单独维护于 [09](09-military-scenarios.md)。

## 1. 需求推导方法

专利要保护的不是"让人确认一下"，而是"协同需求驱动的介入界面组织 + 状态绑定校验 + 局部回写与恢复"这条完整机制链。

能撑起这套机制的需求，必须同时满足以下条件。

| 编号 | 需求条件 | 不满足时的后果 |
| --- | --- | --- |
| R1 人的增量不可替代 | 人带来系统拿不到的事实、专业判断或授权，例如未接入的维修记录、现场经验、业务授权 | 介入界面退化为"确认按钮"，无创新 |
| R2 运行中介入有时效价值 | 现在处理能改变离开前采集的证据、避免二次进场或漏检；延后审核有真实成本 | 离线审核同样有效，介入必要性不成立 |
| R3 自主边界清晰 | 常规避障、规则明确的补拍由系统自主完成，不打扰人 | 被打扰的都是琐事，机制被证伪 |
| R4 介入对象多样 | 一次任务能覆盖参数、计划、条件、执行控制多类介入对象 | 只能演示单点参数修改，权利要求收缩 |
| R5 修改影响可计算可展示 | 改了之后哪些结果失效、哪些保留、从哪里继续，能向用户讲清楚 | 无法演示"受影响集与恢复集分离"这一核心机制 |
| R6 存在真实外部副作用 | 设备指令发出去不能撤回，需要执行回执核查与补偿流程 | 无法演示过期拦截、幂等与副作用核查 |
| R7 空间交互必要 | 需要辨认对象、限定范围、关联空间证据，地图比列表更好 | 地图只是装饰，与仓库地图主线脱节 |

R1 与 R2 是必要条件；R3 是对照组成立的前提；R4 至 R7 决定权利要求能铺多宽。

## 2. 场景筛选框架

候选场景按 R1-R7 逐项打分，只有 R1、R2 成立且 R3 清晰的场景才进入实施例设计。

场景设计遵循三条原则。

1. 先纵向跑通一个场景，再横向验证迁移性，不为迁移性提前抽象通用平台。
2. 每个场景必须保留"自动处理"与"事后离线审核"两个对照组，回答"为什么现在就要人"。
3. 场景只承载需求验证，不据此扩大仓库当前的架构实施范围。

## 3. 场景一（首选）：无人巡检 - 疑点复核与定向补检

本场景与 [06](06-patrol-scenario.md)、[07](07-real-inspection-needs.md) 的收敛方向一致，也是文献证据最强的方向（Air-Cobot、Airbus US9952593B2、GE US10775314B2 都指向"清单外疑点 + 人工追加取证"）。

### 3.1 业务流

无人设备按清单执行例行巡检。

专家在回传证据中发现清单未覆盖的疑点，或有来源的事实与台账冲突。

系统组织有边界的介入界面，专家指定核查目标或补充有来源的背景资料。

系统把目标转为已有能力支持的追加采集任务，回传结果后进入专业核验或保留待核验。

### 3.2 需求映射

| 需求 | 场景中的具体体现 |
| --- | --- |
| R1 | 专家掌握系统未接入的维修背景、构件用途知识；能区分合法改造与真实缺陷 |
| R2 | 设备离场后补采成本高；取证窗口即将关闭；当前判断决定后续采集内容 |
| R3 | 自主避障、常规补拍不发起征询；只有清单外疑点与证据不充分才找人 |
| R4 | 参数（采集参数）、计划（追加检查步骤）、条件（允许区域）、执行控制（暂停与继续）都能出现 |
| R5 | 修改补检目标后，原结论标待复核、无关结果保留、恢复位置由执行器决定 |
| R6 | 设备移动指令与采集动作不可撤回，需要执行回执核查 |
| R7 | 选资产与构件、限定补查范围、关联空间证据 |

### 3.3 交互片段（三张任务卡）

**M1 疑点证据复核**。

系统请求或用户主动发起；绑定资产、构件与证据版本；结论允许"已解释、需补证、转专业核验、暂无法判断"，不只给同意或拒绝。

**M2 追加专项检查与影响确认**。

专家指定检查问题或范围；系统转为已有能力支持的采集动作；不能完成的部分明示缺口；只有真实业务冲突才要求取舍确认。

**M3 台账与现场冲突**。

用户补充有来源的事实；用户声明先作为待验证信息，不一键改成权威状态。

M3 天然演示"临时介入作用域"：用户只能补充证据来源，不能直接修改主台账。

### 3.4 对专利机制的支撑

三张卡分别覆盖三个候选创新点：M1 支撑"协同需求组织"，M2 支撑"局部回写与恢复"，M3 支撑"临时介入作用域"。

## 4. 无人系统内的备选场景（供迁移性验证，不建议首发）

| 场景 | 优势 | 风险 |
| --- | --- | --- |
| 无人机应急搜救 | 任务中调整搜索区域与优先级，时效压力最强 | 需要动态重规划能力，执行端能力假设多；安全责任敏感，取证难 |
| 无人仓储与园区机器人群 | 异常处置与调度授权，副作用真实、并发介入多 | 空间交互偏弱；容易退化成运维工单系统 |
| 无人船水下检测 | 与巡检同构，可复用 M1/M2 任务卡 | 行业数据与访谈资源更难获取 |

建议首发仍用巡检场景，应急搜救作为第二实施例验证机制可迁移性。

军事方向的无人系统候选见 [09](09-military-scenarios.md)。

## 5. 后续场景占位（非无人系统）

## 6. 待确认事项

1. 场景一的行业载体（输电线路、油气管线、园区设施、机库航空器）尚未选定，须先按 [07](07-real-inspection-needs.md) 第 5 节访谈取证再冻结 fixture。
2. M3（台账冲突）是否纳入首批：M3 对"临时作用域"创新点支撑最好，建议纳入。
3. 应急搜救作为迁移验证场景的排期，取决于巡检场景何时闭环。
