# 基于文献的初步研究计划与推进步骤

> 日期：2026-09-29。性质：初步研究计划，非当前架构规范，非已完成实验报告。本文只安排研究和验证，不授权引入新的 Runtime Platform、Surface Lifecycle 或 Recovery 模块。

## 1. 目标与推进原则

先回答一个具体问题：**运行中的 Agent 需要人参与时，怎样让用户知道为什么找自己、这次能改什么、修改后会发生什么，并让实际执行与这一理解一致？**

已确认以无人巡检为主场景，地图从首版参与。先完成 M1“异常核查与条件补充”和 M2“未执行巡检点调整”两张任务卡，再评估其他地图业务的迁移验证。具体原型设定见 [06 主场景说明](06-patrol-scenario.md)，尚未作为真实需求或实现结果验证。

研究主线为：无人巡检任务分析 → M1/M2 任务卡 → 可控原型 → 系统反例 → 用户形成性评估 → 技术交底。状态约束和执行恢复是支撑交互可靠性的机制；不能让研究变成与用户体验脱节的状态管理平台。

本文的阶段、样本数量和时间安排均为建议，尚未执行，也不是交付承诺。

## 3. 研究问题、候选机制与验证映射

| 研究问题 | 文献启发 | 本次要实现和检验的候选机制 | 必须获得的证据 |
| --- | --- | --- | --- |
| RQ1：用户能否迅速理解这次为什么需要自己、能改什么？ | L1、L2、L3 | 根据介入目的和目标对象选择受控编辑组件；显示理由、范围、限制 | 范围理解正确率、首次正确操作时间、查找或误入无关区域的次数 |
| RQ2：任务已变化时，界面如何帮助用户正确处理未提交编辑？ | L2；L6 为复用基础 | 提交前核对相关对象和前置条件；相关变化时解释原因并重新征询，无关变化不无条件废弃编辑 | 相关/无关变化的判别结果、错误状态提交、误拒绝，以及用户能否理解失效原因 |
| RQ3：修改生效后，用户是否知道保留了什么、重做什么、从哪里继续？ | L4；L7、L8 为工程边界 | 在有限依赖关系内生成影响预览；提交后展示实际变更与后续步骤，无法局部继续则明确升级处理 | 预测与实际执行的一致性、重复执行数、用户对下一步的回答及重新理解时间 |

不预设“动态界面一定更好”。第一版也不要求 LLM 生成 UI：先用规则与受控组件验证机制是否有价值。只有遇到规则难以覆盖的真实情境，才增加 LLM 分类或组织建议，并单独记录质量、时延与失败情况。

“最小充分”暂按可检验定义处理：先为每个任务列出完成当前决定必需的事实与操作，界面必须全部覆盖；再减少与本次决定无关的默认展示。允许展开上下文，不追求按钮最少，也不宣称全局最优。

## 4. 无人巡检主场景中的两张任务卡

采用 [06 场景说明](06-patrol-scenario.md)中的候选 fixture：一台模拟巡检车、少量巡检点、通道围挡异常、预设核查方式和后续方案。业务目标是完成可执行的巡检项，并如实保留延期项与异常处理状态；不是让用户为了演示组件而反复确认。

### 4.1 M1：异常核查与现场条件补充

假设用户掌握系统尚未获取的临时施工信息。界面围绕一条异常组织交互；选择核查方式和补充条件可以分支出现，不要求每次都填写全部内容。

1. 展示异常位置、关联巡检点、现场画面或模拟证据，以及当前需要用户判断的问题。
2. 用户选中对应地图对象，补充现场条件，或从实际支持的候选核查方式中选择。
3. 需要说明封闭范围时，先支持选择既有区域；自由圈画按需要加入。几何草稿属于用户提出的候选约束，通过校验、完成影响预览并由用户确认提交后才写入任务条件。
4. 提交前说明仅更新哪些异常信息或条件；若改变任何巡检点状态或后续安排（包括 P3 延期），则进入 M2 预览，不静默扩大本次作用域。M1/M2 可合并为一次确认；取消时丢弃本次整份未提交草稿，先前已接纳的变更不会被自动撤回。
5. 提交后显示实际接纳内容和后续状态。等待期间若相关条件变化，应展示差异并重新确认；无关日志更新不应使编辑失效。

验收：界面对象、提交对象和实际变更对象一致；补充信息不等同于异常已经排除；取消、越界、重复提交、相关与无关变化均有可复查结果。

### 4.2 M2：调整受影响的未执行巡检点

仅当 M1 的现场条件或用户主动请求影响后续任务时进入。使用显式状态与有限依赖的 fixture；后续候选方案预先给定并校验，不要求自动路径规划。

1. 地图和任务列表共同突出受影响的未执行巡检点，显示已完成项以及当前执行状态。
2. 用户从允许的延期、保留或候选顺序中调整，不能以普通编辑方式改写已完成记录或已执行动作。
3. 预览哪些检查记录保留、哪些任务延期、哪些候选路径或后续步骤需重新校验。
4. 提交时复核相关对象状态和条件。合法修改接纳后，由模拟执行器选择可用继续位置，并回报实际采用的方案。
5. 没有有效候选方案、依赖不明或执行端不支持继续时，明确进入等待或重新确认；不得把“已接受调整”显示成“车辆已执行”。

验收：延期项保留为未完成；仍有效的已完成记录没有被清空；过期选项不能执行；实际继续路径与提交后反馈一致，失败可解释。

### 4.3 三类地图交互与迁移范围

“选对象、改空间条件、调后续任务”是同一主场景中的可组合能力，不是三个必经弹窗。地图对象关联和高亮先行，已有区域选择与固定候选方案其次，自由绘图等编辑能力按任务需要加入。

M1/M2 分别承接现有 EXP-002 征询等待和 EXP-004 打断纠偏中的研究问题，不把完整闭环提前写为已实现。02 中的参数/计划/几何例保留为技术解释；其参数查询例不再决定主业务场景或推进顺序。

主场景成立后，再从应急资源安排、物流配送等地图业务中选择一个有实际依据的迁移案例；当前不固定第二领域，不要求做纯数据分析场景，也不提前宣称跨领域通用。

## 5. 当前仓库的实施边界

仓库当前基线为 Web Workbench → 薄 CopilotKit Runtime → AGUIMock / single-agent-chat-server；另有独立 dev-only `map-validation-agent`。研究方案以 `AGENTS.md`、当前 ADR 和代码事实为边界。

建议按以下顺序承接现有工程：

- 先复用 AGUIMock 的确定性场景与 Workbench 的展示能力，检查交互本身；不让模型随机性掩盖 UI 问题。
- 保留 SACS profile 的能力差异；不由前端或 Runtime 伪造未支持的 Frontend Tool 调用。
- 需要真实模型时，在独立 dev-only 验证路径核验；不把研究执行器嵌入 CopilotKit Runtime。
- 临时作用域、失效和恢复等新机制先在隔离研究原型中验证。进入产品代码前逐项回答 Feature admission gate；本计划不是这些平台能力的准入决定。
- 实验观察写回已有 EXP-002 / EXP-004 的相应问题或附件；不另建一套竞争的交互模式目录。单次原型成功不直接写成 `docs/reports/` 的成熟结论。

当前 EXP-002 已有工程基础，但真实 provider 及人类观察仍需实际验证；EXP-004 的完整纠偏闭环仍待实现。应把“已有基础”“本次新增”“仍未支持”分开记录。

建议预留约 4—6 周：P0/P1 放在第 1 周，P2 在第 2—3 周，P3 在第 3—4 周，P4 在第 4—5 周，P5 在第 5—6 周，可按依赖交叠。每阶段以产出和验收为准；兼职投入、招募和接口差异会影响历时。

## 7. 公平对照与机制消融

### 7.1 先比较交互，再比较执行机制

| 条件 | 用户界面 | 后台和任务控制 | 用途 |
| --- | --- | --- | --- |
| B1 通用结构化编辑 | 完整但可用的地图与任务面板，含相同证据、标签和帮助 | 与候选方案使用相同合法操作、校验、场景与执行器 | 主对照；检验情境化组织是否真的有价值 |
| B2 候选介入交互 | 按本次目的组织必要信息与操作，显示范围及影响 | 与 B1 相同 | 主实验条件 |
| B0 文本协作，可选 | 清楚的文字提示及输入，不故意写得含糊 | 仍有相同合法操作与实际确认机制 | 了解相对对话方式的差异；不作为唯一弱基线 |

优先选择参与者内比较，使用难度相当但内容不同的任务变体并平衡呈现顺序。保持训练、地图数据、现场证据、事实信息可获得性、控件可用性、视觉质量和故障频率可比。模型输出先固定；接入真实模型后，把模型失败、工具失败与交互失败分别编码。

### 7.2 两类消融分开进行

- **用户侧消融**：在 B2 中分别去掉“影响预览”或“恢复后摘要”，保留相同执行语义和校验；观察理解错误和重新理解时间是否变化。不要同时删掉多个机制后归因于其中一个。
- **系统侧消融**：在无外部副作用的回放环境比较粗粒度全局版本拒绝与相关对象校验，比较完整重算与受影响范围重算。所有分支均需合法校验；缺失校验的故障注入仅用于说明失效路径，不用来充当真实部署基线。

如果候选方案的优势只来自基线漏校验、少展示事实或故意重做全部工作，应调整对照，不据此报告方案优越。

## 8. 指标、日志与真实数据要求

| 指标 | 采集方式 | 解读限制 |
| --- | --- | --- |
| 范围理解正确率 | 操作前回答“这次能改什么、不能改什么”，按冻结答案评分 | 是本任务的理解指标，不直接声称测得总体态势感知 |
| 首次正确操作时间 | 从介入内容完整可见到第一次有效提交 | 同时报告失败和取消，不能只统计成功者 |
| 影响预测正确率 | 提交前判断哪些步骤保留/重做，与实际日志比对 | 不能用 UI 声称的影响替代执行真值 |
| 重新理解时间 | 返回任务后回答当前状态和下一步所需时间 | 如加入分心任务，应标准化且单独说明 |
| 过期提交与误拒绝 | 对相关变化、无关变化分别统计尝试、拒绝和接受 | 两类变化必须都有；一律拒绝并不代表设计好 |
| 重复执行与无关重算 | 比较预期受影响集合与实际执行节点清单 | “最小受影响集合”先限定在人工可核对的有限 fixture 中 |
| 主观困难与可控感 | 简短量表配合回顾访谈，逐条保留原始答复 | 自编问项只能按本次问项解释，不能冒充标准量表 |

最小日志应包含匿名参与者编号、条件、场景版本、任务/请求关联标识、呈现时间、操作时间、目标对象、允许范围、提交载荷、校验结果、前后状态差异、实际执行步骤、取消或失败原因，以及模型/提示词/代码版本。实现时复用已有 ID，不为记录实验强行建立新的产品领域模型。

原始数据、清洗规则与汇总表分开保存；错误和不支持的情况也进入结果。先冻结排除规则与主要指标，再看正式结果。样本量依据先导方差、最小有意义差异及可招募范围制定；正式报告同时给出不确定性，不只展示均值。

可以合成场景、输入和故障，必须标为 fixture 或模拟。人的操作记录只能来自真实参与；LLM 扮演用户仅用于预演脚本，不能替代用户实验、生成满意度或补齐显著性数据。

## 9. 暂无业务人员时怎么开展

先用普通开发者或有复杂工具使用经验的人验证“能否理解修改范围、发现状态变化、预测后果”这些通用交互问题。统一提供领域说明和练习，记录参与者背景。

同时由研究者把每项业务假设写清，例如“允许延期未执行巡检点但不得改写完成记录”“后续候选方案已按模拟约束校验”。这些是假设与实验约束，不能写成访谈得到的真实业务需求。

此阶段能够支持“受控任务中的可用性与机制可行性”，不能支持“专业无人系统操作员负荷降低”或“真实任务效能提升”。若后续一直无法接触业务人员，就收缩结论范围；地图实施例保持模拟，不制造业务需求证据。

## 10. 第一周行动清单

## 11. 技术交底里程碑与调整条件

| 里程碑 | 可交付材料 | 继续或调整依据 |
| --- | --- | --- |
| K1 问题与边界清楚 | 用户困难、两张任务卡、来源和工程能力表 | 如没有需要专门组织交互的问题，先回到需求分析 |
| K2 机制链可解释 | 触发、作用域、界面、操作校验、实际变更、继续位置的完整实施例 | 如仅剩常规表单与原生 interrupt 接线，不以宽泛组合宣称创新 |
| K3 正反例可重现 | 正常/失效/冲突/无法恢复的事件轨迹与状态差异 | 如依赖无法确定，收缩到显式依赖的任务类别，或取消局部恢复承诺 |
| K4 技术交底初稿 | 技术问题、机制步骤、关键数据结构、正常与异常附图、替代方案、现有技术差异表 | 交底讨论依据是具体机制与证据；原型成功不自动证明创造性 |
| K5 差异与效果复核 | 对照数据、反例结果、适用边界及更新后的权项讨论稿 | 交互无收益则简化界面；系统效果有收益则准确限定效果，不强行编造认知收益 |

停止或转向的明确条件：

1. 新检索到的单件公开材料已明确覆盖核心关系，且找不到进一步可解释的技术差异：收缩或更换候选发明点。
2. 与公平的通用编辑界面相比，任务正确性和理解没有改善，交互步骤反而增加：删除多余组织机制，重新验证真实困难。
3. 只有重建通用 Runtime 才能完成第一例：缩小原型范围，回到当前架构准入问题，不继续扩大平台。
4. 参数或计划的作用范围无法可靠判定：降级为明确边界的修改，不让 LLM 自行扩大可写范围。
5. 无法获得所需参与者或真实业务依据：保留系统可行性结论，延期或缩小用户与业务效果主张。

第一步应先按 06 的场景草稿完善两张任务卡与反例，不急于写最终权利要求。它们会直接揭示目前的“状态绑定、作用域受控、连续恢复”是否真正帮助用户完成一次协同。
