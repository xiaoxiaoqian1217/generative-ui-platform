# 双入口巡检任务脚本与交互走查 v0.1

> 日期：2026-09-29｜状态：文献启发的模拟脚本，尚未开展参与者走查。
>
> 本文把 06 中的候选任务卡补成可逐步演练的脚本。飞机外观巡检仅作为有文献依据的具体载体，不代表用户已选定航空行业，也不是航空维护规程。编号、记录、能力、状态和分支均为研究设定；没有真实设备执行、诊断或用户效果数据。

## 1. 本轮先验证什么

**先走脚本 B：检查员主动追加清单外检查；再走脚本 A：Agent 请求核实现场与资料的差异。** 保留 A/B 编号以对应此前讨论，优先级不由编号决定。

| 脚本 | 人的目的 | 人具体贡献什么 | 本次操作的结果 | 为何在运行中参与 |
| --- | --- | --- | --- | --- |
| B：主动追加局部检查 | 对例行清单未覆盖的部位取得可复核证据 | 提出新的检查目标，并指定构件和范围 | 新采集任务被接纳、执行，证据归到正确对象 | 人在现场检查中提出当下需求；机器人仍在作业。能否减少再次进场须另行验证 |
| A：请求核实资料差异 | 解释某个附加件为何与当前记录不一致 | 核对单机身份与有出处的变更资料；或明确无法判断 | 本次差异得到有来源的解释，或保留待核验 | 可以运行中异步回答；目前不足以证明必须立即处理，不默认暂停 |

两个脚本检验交互是否清楚、操作是否准确生效，不用它们预先证明“动态界面优于固定面板”。用户也可以主动核查差异，Agent 也可以请求确定补检范围；发起方式与参与目的仍是两个维度。

## 3. 共用场景、材料与能力

### 3.1 对象和初始状态

演练使用虚构机库 H-SIM、飞机 AC-SIM-01 和移动检查设备 R-SIM-01。地图先定位飞机，再联动构件图与证据卡；不在二维地理地图上圈画立面缺陷。

| 对象/任务 | 确定的模拟含义 | 初始状态 |
| --- | --- | --- |
| AC-SIM-01 | 本次检查对象；与相邻的 AC-SIM-02 明确区分 | 本次任务所属资产 |
| PANEL-L1 | AC-SIM-01 的左侧外表面区域 | 不在本次例行清单中 |
| SEAM-L12 | PANEL-L1 相邻的指定接缝区域 | 不在本次例行清单中 |
| ANT-02 | AC-SIM-01 的外部附加天线；示例位置仅用于关联 | A 的资料差异对象 |
| T0 | 已完成的例行采集，结果 E0 | 已完成 |
| T1 | 正在进行的例行图像采集 | 执行中 |
| T2 | 后续例行图像采集 | 未开始 |

A 和 B 分别从独立快照开始，不能让 B 的操作污染 A 的初始状态。主流程没有告警触发的紧急停车条件；真实设备安全状态一旦不同，应由原有控制链处理，不能套用本脚本的继续规则。

### 3.2 主持人需要提供的材料卡

以下文字可直接用作桌面走查卡片。它们给出参与者应获得的事实，不要求参与者凭虚构图像做专业诊断。制作视觉原型时再替换为明确标注的合成图或获准使用的脱敏材料。

| 卡片 | 卡片正文/内容要求 | 谁可获得 |
| --- | --- | --- |
| MAP-1 | H-SIM 内有 AC-SIM-01、AC-SIM-02；每个构件只属于一架飞机；选中资产可打开构件图 | 人与系统相同 |
| TASK-1 | T0 已完成，T1 执行中，T2 未开始；当前采集结束后可插入支持的补采；同一设备一次只执行一个采集动作 | 人与系统相同 |
| OBS-B1 | 检查员在自己的现场检查中注意到 PANEL-L1 的疑似表面起伏，要求保留该区域及 SEAM-L12 的三维形貌以供后续复核；机器人未发出告警 | 人的本次新观察与新目标；表达后成为系统输入，不宣称模型本可判断却被禁用 |
| E-A1 | ANT-02 的当前图像卡：存在与旧单机记录不同的外部附件；不能仅据此判断正常或故障 | 人与系统相同 |
| DB-A1 | 当前可访问单机记录没有 ANT-02 变更项；系统已查单机身份、可访问记录和图像质量，仍不能解释差异 | 人与系统相同；若同步已成功，不再使用“缺少记录”的主分支 |
| R-A1 | 模拟交接记录 M-SIM-17：资产 AC-SIM-01、对象 ANT-02、变更项“新增附件”、位置与 E-A1 一致、交接来源和版本 r1；未提供结构或适用性结论 | 本轮设定为检查员收到但尚未进入查询接口的记录；提交后双方都可见，不能故意隐藏已可查询资料 |
| CAP-1 | 模拟支持：图像采集、指定区域三维形貌采集；不支持材料内部检测。可预先接纳后续任务；执行中采集不可原地改参数，结束后才开始下一采集动作 | 人与系统相同；是模拟能力，不是仓库现有机器人能力 |

图像卡是对所需材料的说明，不冒充已取得的照片或检测结果。参与者的任务是对象关联、范围表达和执行理解；专业判断有效性需要真实检查员及真实材料另测。

### 3.3 谁做决定，什么可以继续

用户决定本次追加目标、检查范围或复核意见；执行系统负责可达性、能力匹配和采集动作安排。LLM 可以解释意图，但不能把“相邻部位”自行扩展成整架飞机。

T1 在用户查看和编辑期间继续。T2 是否后移，只能依据已接纳的补采安排显示；打开编辑卡本身不改变计划。模拟中原任务与新增区域无诊断依赖，T0/E0 保留。不能把“当前动作结束后插入”描述成任意位置恢复。

## 4. 脚本 B：人主动追加清单外检查

### 4.1 给参与者的任务

你正在检查 AC-SIM-01。机器人正常采集 T1，没有请求你参与。你在自己的现场检查中发现 PANEL-L1 值得进一步核查。请让机器人取得 PANEL-L1 和相邻 SEAM-L12 的三维形貌，保留原来的例行检查；不要求你判断缺陷是否成立。

可用表达示例：“把这块外表面和旁边这条接缝加入本次检查，采三维形貌供复核。先完成正在做的采集，原来的检查保留。”参与者不必逐字照念。

### 4.2 主持人按六帧推进

| 帧 | 系统与界面呈现 | 用户可以做什么 | 主持人/模拟执行器的状态变化 |
| --- | --- | --- | --- |
| B1 正常运行 | 地图显示 AC-SIM-01，任务面板显示 T0/T1/T2；主动输入和对象选择可用，没有待答请求 | 选择飞机，再在构件图选择 PANEL-L1；主动输入要求 | 保持 T1 执行中，不自动生成告警 |
| B2 解释范围 | 显示“本次新增检查”，目标 PANEL-L1；“相邻部位”需明确到 SEAM-L12，允许纠正 | 确认或重选相邻接缝；补充目的 | 得到两个明确对象；未提交，不创建任务 |
| B3 预览变更 | 新增 PANEL-L1/SEAM-L12 的形貌采集；T1 结束后执行，T2 后移，T0/E0 保留；结果将用于复核 | 查看影响，提交，或取消 | 提交时重新核对对象、能力、前置条件与重复任务 |
| B4 接纳 | 显示补采 B-N1/B-N2“已接纳，等待 T1 完成” | 查看结果要求或返回任务面板 | 只在接纳成功后改任务清单；此时不得显示已采集 |
| B5 执行与回传 | T1 完成后依次显示 B-N1、B-N2 执行中；各自返回证据 E-B1、E-B2 | 查看证据与所属构件；不必守着弹窗 | 每个动作回传结果后才标记取证完成，随后继续 T2 |
| B6 回到主任务 | 显示“两个区域的证据已返回，待复核”；T2 恢复原定工作；T0/E0 可查询 | 判断是否还缺证据，或留待专业复核 | 本轮采集请求已完成，疑点是否成立仍未判定 |

上述六帧也是第一版文字故事板。界面采用常驻任务摘要、地图/构件选择、按需展开的介入卡，不要求每帧产生新对话框，也不要求 LLM 动态生成布局。

### 4.3 成功标准与精确变化

| 项目 | 主分支期望结果 |
| --- | --- |
| 对象 | 只新增 AC-SIM-01 的 PANEL-L1、SEAM-L12；AC-SIM-02、ANT-02 不受影响 |
| 任务 | T1 正常完成 → B-N1 → B-N2 → T2；T0 不重做 |
| 证据 | E-B1 对应 PANEL-L1，E-B2 对应 SEAM-L12；都记录本次请求标识和采集任务 |
| 状态 | 已接纳、执行中、证据已返回可区分；没有把证据返回写成缺陷排除 |
| 用户理解 | 能指出新增加了什么、何时执行、哪项后移、哪些结果保留 |

取消草稿也是合法完成路径，此时任务和证据均不改变，不将其计为成功发起补采。用户要求内部检测时应说明能力缺口、记录待专项处理；不能用三维表面采集冒充内部检测。

## 5. 脚本 A：Agent 请求核实资料差异

### 5.1 给参与者的任务

机器人发现 AC-SIM-01 的 ANT-02 与当前单机记录不一致，已有自动核对仍不能解释。你收到交接记录 R-A1。请核对记录是否对应这架飞机和这个附件，决定如何记录本次差异；不要据此判断整机适用性。若资料不足，可以明确留待核验。

人的增量是核对并提供当前未同步的具体记录。若系统已经能取得并校验该记录，应优先走自动处理反例，不把简单数据库查询包装为人的专长。

### 5.2 主持人按六帧推进

| 帧 | 系统与界面呈现 | 用户可以做什么 | 主持人/模拟执行器的状态变化 |
| --- | --- | --- | --- |
| A1 提出核查 | 非阻断请求 A-R1 关联 AC-SIM-01/ANT-02；显示“当前记录未包含该附加件，是否有匹配的变更资料？” | 打开、暂后处理；也可继续自己的工作 | T1 继续；请求未答不自动变成拒绝、同意或任务暂停 |
| A2 核对依据 | 地图定位飞机，构件卡显示 ANT-02；E-A1 与 DB-A1 并列，列出已核对项 | 查看身份、来源与版本；提交 R-A1，或表示没有可靠依据 | 保存草稿，不改权威台账，不关闭疑点 |
| A3 明确处理 | 显示 R-A1 中匹配的资产、部位、变更内容；意见为“按此记录，本次外观差异可解释” | 提交有来源的复核意见，或改为待核验 | 核对记录关联和当前证据；用户不能只点“正常”掩盖依据缺失 |
| A4 保存结果 | 显示“本次差异已解释，依据 M-SIM-17；主台账同步待处理” | 查看影响或返回主任务 | A-R1 记为已答复，疑点记为本次人工复核已解释；只写本次记录 |
| A5 后续检查 | T1/T2 依原计划继续；无自动新增补拍 | 若认为证据仍不足，可另提补采目标 | 新目标按 B 的采集流程处理，并保留与 A-R1 的关系，不重复回答原请求 |
| A6 结束核查 | 复核历史保留 E-A1、DB-A1、R-A1 和处理意见 | 可追溯“解释依据是什么” | 不生成整机正常、缺陷排除或台账已同步等额外结论 |

### 5.3 成功标准与退出路径

主分支只增加复核记录和 A-R1 的答复状态，不新增采集、不重跑 T0，也不因核查占用暂停整个任务。记录匹配可解释“为何与旧资料不同”，不自动证明附件状态良好。

没有可靠记录、记录属于 AC-SIM-02 或证据不足时，正确结果是“待核验＋原因”，不是强行得出正常/故障结论。用户可以退出即时处理；是否通知其他岗位、修改台账或安排人工检查，待实际流程确认后接入，当前不显示已派单。

**A 目前是异步核查脚本，不是实时中断必要性的正例。** 如后续证据证明当前答复会改变离场前的采集，另写运行中补采变体；如果始终适合巡检后审核，就保留为异步对照。

## 6. 任务推进时，用户的编辑如何处理

所有事件按操作节点触发，不用随机倒计时制造失败。每次只注入一个变量，并保存变化前后状态。

| 变体 | 注入时机与事件 | 期望界面和处理 | 不允许的结果 |
| --- | --- | --- | --- |
| B-C1 已接纳任务开始执行 | 独立重置到 B-N1 已接纳但未开始；用户打开“取消 B-N1/B-N2”，提交前 B-N1 开始执行 | 显示“B-N1 已开始，本设备不能中途取消；B-N2 仍可取消”。尚未取消任何项；让用户选择仅取消 B-N2 或放弃本次修改，再次提交时重验 | 把两项都显示已取消；静默部分成功；重启全部任务 |
| B-C2 编辑中能力改变 | B3 草稿期间，形貌采集能力变为不可用 | 保留目标与说明，停止接纳该采集；显示能力缺口与待安排出口 | 用照片替换用户要求而不说明；谎报已排队执行 |
| A-C1 依据关联改变 | A3 草稿期间，新版本 R-A1/r2 指明该记录属于 AC-SIM-02，旧关联已撤回 | 保留用户草稿但禁止按 r1 关闭 AC-SIM-01 疑点；展示变化，要求重新核查或留待核验 | 只看用户点过提交就写入“已解释” |
| U1 无关更新 | 任一草稿期间，其他资产遥测更新，目标、证据和能力不变 | 草稿与合法操作保持可用 | 因全局版本变化强迫重新填写 |
| B-C3 原动作自然完成 | B3 草稿期间 T1 完成、T2 开始；原意是“当前采集结束后追加” | 更新插入点到 T2 之后并显示影响；若用户明确要求 T2 之前，则显示该条件已无法满足并请用户改选 | 默认任务推进就是编辑过期；无视明确时序要求 |
| D1 重复提交 | 对已成功接纳但回复延迟的请求重复提交 | 返回同一结果；B 仍只有 B-N1/B-N2，A 只有一条本次答复 | 重复采集或重复写入 |
| X1 双入口并存 | A-R1 待答，用户主动追加 PANEL-L1 检查 | 新请求关联 PANEL-L1，A-R1 保持待答；同一对象时另外校验冲突 | 把新增检查自然语言误当成 A-R1 的答案 |

B-C1 走查顺序：打开变更 → 注入任务开始事件 → 提交旧草稿 → 看差异 → 选择可执行部分 → 重新提交 → 看实际结果。这个分支检验的是“用户如何理解并处理变化”，不是单纯证明后台能拒绝旧请求。

若用户重提“仅取消 B-N2”并被接纳，期望结果是 B-N1 完成并保留证据、B-N2 已取消且没有新采集结果、随后继续 T2。用户放弃修改则保留原补采安排。两者都不能显示“全部取消成功”。

## 7. 最小操作记录和人工核对表

以下是走查记录字段，不是新协议或产品领域模型。原型中优先复用已有 ID、状态与日志能力。

| 字段 | 用途 |
| --- | --- |
| session / script / variant / condition | 区分实际走查、脚本及界面条件 |
| initiator / purpose / requestRef | 区分谁发起、做什么、是否回复某请求 |
| asset / component / evidenceRevision | 核对地图、证据和修改目标一致 |
| before / proposed / accepted / observed | 分别记录原状态、用户提议、系统接纳和执行器实际结果 |
| event / time / reason | 保存状态变化、动作时间及拒绝或排队原因 |
| userAnswer / observerNote | 原样记录用户理解与观察；研究者解释另列 |

每条脚本结束都核对四件事：用户想改什么、系统接纳什么、实际上完成什么、还有什么未完成。对 B 主分支，预期的变更集合就是新增 B-N1/B-N2 及相应证据；对 A 主分支，就是一条有来源的复核意见与对应请求答复。

## 8. 走查方式、反例和验收

### 8.1 第一次怎么走

1. 主持人准备第 3 节材料卡、空任务清单和记录表。先跑 B 主分支，再跑 B-C1，最后跑 A 主分支及 A-C1。
2. 给参与者业务目标和能力说明，隐藏主持人的操作顺序及期望答案；第一次不提示按钮位置。没有外部参与者时可自查脚本，但只记录为研究者预演。
3. 提交前请参与者说明“会改谁、什么时候执行、哪些保留”；反馈后说明“现在实际完成了什么”。这属于有提示的形成性走查，不能把耗时直接作为正式无提示实验数据。
4. 主持人逐帧记录对象错误、误解、等待与状态；不能代替参与者判断后再记为独立完成。
5. 保留失败和无法判断路径，修订脚本。全部结果栏保持空白，直到实际执行后填写。

### 8.2 必须能通过的反例

| 反例 | 正确行为 | 要防止的偏差 |
| --- | --- | --- |
| 普通通道受阻且可自主绕行 | 导航自行处理 | 用普通障碍制造人工参与 |
| 图像质量不足且已有自动补采规则 | 执行既定补采 | 每次补拍都要求审批 |
| ANT-02 的匹配变更记录已可查询并通过校验 | 自动解释资料差异，可供人查看 | 刻意不给系统信息以凸显人的价值 |
| 用户仅查看历史或保存非执行备注 | 不改变任务，不暂停 | 把所有交互都当作干预 |
| 用户取消未提交草稿 | 原计划不变 | 开始编辑就偷偷改任务 |
| 运行结束后审核即可满足需求 | 允许异步集中审核 | 把所有核查强制变成实时征询 |

### 8.3 对照要保持什么相同

后续 B1 固定面板与 B2 情境化介入卡使用同一组对象、证据、操作权限、执行能力与后台校验。B1 同样提供可用的地图联动、状态提示和错误反馈；差异限于信息与操作如何围绕当前目的组织。不能给 B2 独占事实或让 B1 故意漏校验。

单次走查通过意味着脚本和交互可理解，不意味着专业需求成立、用户负荷降低或专利创造性成立。正式比较前准备等价任务变体并平衡顺序，避免重复同一材料造成记忆优势。
