# 候选创新点与专利深化路线报告

日期：2026-09-29。性质：研究假设与技术交底准备，尚未形成正式权利要求或可专利性结论。

## 1. 阶段判断

值得继续研究的是：**一次协同需求怎样决定用户可见的信息、可执行的修改，以及修改后的任务影响，并让这三者始终对应同一个任务对象。**

“状态绑定的受控介入界面 + 局部恢复”仍可作为工作方向，但它不是已经被证明的新组合。状态绑定、结构化回复、过期处理、检查点恢复等都有现成机制；必须比较实际技术关系，不能只把已有步骤串得更长。

本次复核还补入了非专利资料压力：既有协议能力见 [02 第 4.5 节](02-interaction-model.md#45-与现行协议和执行框架的衔接)。本报告不将这些基础能力单独作为创新。[S1]

专利事实和权项位置以[03 对比报告](03-patent-comparison.md)为准；这里讨论的是我们准备怎样改进、怎样检验。

应用验证已按后续讨论确定为地图优先、无人巡检主场景，见 [06 场景说明](06-patrol-scenario.md)。这项选题决定不改变本报告的差异假设，也不意味着“使用地图”本身构成创新。

## 2. 候选点及其可证伪条件

| 候选点 | 具体交互问题 | 候选技术机制 | 差异假设与主要压力 | 预期效果与验证 |
| --- | --- | --- | --- | --- |
| 协同需求驱动的组织 | 用户收到“请确认”，却不知道要解决什么 | 把目的、目标对象、所需决定、缺失信息与执行影响组织成同一上下文 | 若只是把 `reason` 映射成组件，差异弱；需证明更细的对象关系怎样参与组织 | 判断本次目标的正确率、遗漏信息次数；与同信息量固定表单比较 |
| 临时介入作用域 | 参数可改范围与任务实际允许范围不一致 | 从目标对象、可变字段、依赖约束及用户权限计算本次修改集合 | 普通字段白名单和权限控制已常见；需证明范围如何随执行情境变化且可重复计算 | 越界修改接受率、合法修改误拒率、范围推导可追踪性 |
| 与相关状态绑定 | 旧选择已经不适用；无关日志更新却也会使界面作废 | 记录本次决定的相关状态读取集合与语义前置条件，在提交边界重验 | 全局版本比较属于较弱基线；细粒度并发控制也不是新概念，需检索其在介入界面的结合 | 过期提交接受率、无关变化误失效率、并发冲突分类 |
| 回写与连续性 | 用户改了一个值，却不清楚哪些结果重做、是否重复执行 | 结构化变更定位目标，求受影响依赖集合并由执行器选择合法恢复边界 | 检查点、增量计算和工作流恢复都有积累；不能以“有 Resume”作为差异 | 无关步骤重复数、应失效结果残留数、重复副作用、恢复失败原因 |
| 最小充分交互 | 全量控制台难找重点；精简过度又丢失决策依据 | 根据任务需求标签选择信息与操作，保留必要的影响说明和可展开证据 | 信息减少本身是 UX 原则；需给出“充分”的明确覆盖条件 | 必要信息覆盖率、判断错误、任务耗时、主观负荷；不能只数控件 |

表中均为预期效果。当前无实测改善比例，不预设“显著提升”。如果固定界面同样有效，或候选机制只增加理解成本，应保留负结果并收缩方案。

## 3. 主组合建议：围绕同一份介入约束贯通三端

建议优先深化一份可验证的“介入约束描述”，让它贯通三个环节：

1. **组织界面**：依据本次可改对象、所需证据和操作目的，产生可见信息和允许操作。
2. **提交校验**：用同一目标标识、允许修改集合及相关前置条件判断操作仍有效。
3. **反馈影响**：执行器据实际变更和依赖关系返回保留、失效、待重做及恢复状态，更新原介入记录。

这里可研究的关系是“同一约束如何贯通”，而不是发明又一个权限表、表单框架或通用恢复引擎。以下是候选形式化描述，均为本研究提出的定义，尚未证明创新：

- 本次可修改集合 `W = 请求涉及字段 ∩ 当前阶段可变字段 ∩ 用户已有权限 ∩ 业务可修改约束`。空集时不能生成可提交编辑器；应解释原因或提供其他合法路径。
- 决策依赖集合 `R` 包含决定当前选项和约束所需的事实，不机械包含所有任务日志；约束版本和依赖定义自身也要纳入校验。
- 提交变更 `Δ` 的写入位置必须属于 `W`，且提交时 `P(current[R])` 仍成立。校验、写入、消费本次操作资格必须具有一致的提交边界。
- 受影响集合 `A` 从被改输入沿显式依赖关系传播。依赖不完整或不可逆外部操作存在时，不承诺精确局部恢复。
- 界面集合 `U` 覆盖当前需要理解和完成的事项。不能为了降低控件数，移除关键风险、数据来源或影响说明。

这些集合不是必须采用的实现接口。首个原型可以用规则表和固定依赖图证明闭环，再决定是否值得引入自动推导或 LLM。

## 4. “最小充分”应怎样落地

不要声称找到了全局最小界面。建议先采用可解释的必要集合：

| 输入 | 例子 | 对界面的要求 |
| --- | --- | --- |
| 待完成决定 | 将搜索半径从 500 米改到 800 米 | 半径输入、单位、提交与取消 |
| 判断必需事实 | 当前值、允许区间、触发介入的原因 | 摘要始终可见 |
| 操作边界 | 不能改目标和已确认约束 | 只读边界说明，服务器仍校验 |
| 影响信息 | 重新执行搜索及依赖汇总 | 提交前给预计影响，提交后给实际结果 |
| 可选证据 | 历史参数、详细日志、地图解释 | 可展开查看，不能阻止必要操作 |

原型记录每个组件覆盖哪个需求标签。无组件覆盖的必要标签属于失败；一个组件重复覆盖某标签不自动算冗余，还要看它是否服务不同理解任务。

若后续需要优化，可把选择组件视为带信息覆盖和布局约束的优化问题，但这是待研究的方法，不应先写成已实现算法或已有实验结论。

## 5. 初步独立权利要求技术链骨架

以下供技术交底讨论，不直接作为申请文本：

1. 获取运行中任务的状态、目标对象及可变属性信息，识别一次具体协同需求。
2. 依据该需求、目标对象和当前执行约束，确定本次介入的允许修改集合，以及决定该集合适用性的相关状态和前置条件。
3. 根据上述集合与协同目的组织介入界面，将可操作项映射到目标对象的允许属性，绑定相关状态前置条件与介入标识。
4. 接收结构化用户操作，校验其映射、允许范围、相关状态及操作资格；不满足时不执行变更，并输出原因或更新后的介入请求。
5. 满足条件时，在一致的提交边界内更新允许范围内的状态，记录该介入已被消费、实际变更及失效标记；若影响分析异步完成，同步设置待校验屏障，阻止下游继续消费可能过期的结果。
6. 根据变更与任务依赖关系完成影响分析并确定合法恢复边界；无法局部恢复时进入明确的扩大重算、重新确认或人工处理路径。
7. 继续任务，并将实际生效内容、保留内容、重做范围及继续状态反馈给用户。

必须说明每个步骤的数据从哪里来、由谁计算、失败如何处理。仅用“智能识别”“动态确定”“安全恢复”等结果性用语无法解释实现。

独立权利要求未必需要包含所有候选细节。先让实施例闭环，再与代理人判断哪些技术关系构成解决问题的必要特征；不要为了看起来完整无限增加限制。

## 6. 从属机制与优先级

| 优先级 | 候选机制 | 深化理由 |
| --- | --- | --- |
| 首批 | 相关状态前置条件、消费与幂等记录、影响说明 | 直接影响“操作是否仍有效、是否生效一次、用户是否知道结果” |
| 首批 | 异常对象、核查条件及未执行巡检点的映射，合法继续位置 | 支撑 M1/M2 任务卡，检验界面对象与执行对象是否一致 |
| 后续 | 最小充分组件组织及证据展开 | 需要任务分析和用户数据才能证明有效 |
| 首批基础、逐步深化 | 地图对象 ID、空间条件及局部编辑范围 | 主场景先验证选点/已有区域绑定；几何编辑需要时再加入，不提前建设通用 GIS 能力 |
| 后续 | 阻塞/非阻塞及多次介入协调 | 需要真实并发或持续任务需求，不预先扩成调度平台 |
| 暂缓 | 用户认知状态推断、任意任务图自动失效传播、通用恢复平台 | 输入不可靠或范围过大，会稀释交互课题 |

## 7. 技术效果分开验证

### 7.1 交互效果

观察用户能否说明“当前改什么、不能改什么、提交后影响哪里”；记录错误决定、查找信息时间、完成时间与主观负荷。控件少、点击少不自动意味着体验更好。方案范围错误地限制用户时，也要记录用户无法完成任务的情况。

### 7.2 系统效果

通过可重放脚本检验：过期与越界提交是否被拒绝、无关更新是否仍允许提交、重复提交是否产生重复逻辑变更、失效传播是否遗漏或过宽、恢复是否重复有副作用的动作。

状态提交成功不等于外部工具执行成功。跨服务不承诺天然 exactly-once；应区分已接受、已持久化、已继续、执行失败，并通过幂等键、持久记录与补偿策略处理可恢复部分。

执行框架的恢复限制见 [02 第 4.5 节](02-interaction-model.md#45-与现行协议和执行框架的衔接)。本方案的“确定恢复位置”只指合法的节点/检查点边界，不指精确从任意源码行继续，更不等于 LLM 后续输出确定不变。[S2]

## 8. 下一阶段交底材料清单

1. 两个主实施例：开始状态、协同原因、用户操作、字段变更、失效集合、恢复结果。
2. 一份数据字典：目标对象、作用域、相关状态、介入界面、操作、回执之间的关系。
3. 一份正常流程和四个反例：过期、越界、重复提交、不能局部恢复。
4. 一份证据矩阵：每个候选特征对应公开资料位置、差异假设和待查事项。
5. 一份原型记录：接口版本、规则版本、完整事件轨迹和实际失败，不填模拟改善数字。
6. 一份技术效果说明：把观察结果与原始数据关联，区分工程正确性和用户收益。

具体顺序、工期假设和验收见[05 文献计划](05-literature-plan.md)。

## 9. 继续、收缩或换方向的判断条件

- **继续**：两个实施例都能用同一约束关系闭环，且差异比较能指出具体机制，而非名称不同。
- **收缩**：只在参数编辑场景成立，就先把保护对象限定到该场景，不声称通用计划修改。
- **改写主创新**：相关公开资料已完整说明同一机制，或区别只是更换 Agent/地图/组件名称。
- **转为工程成果**：体验有价值但专利差异薄弱，保留设计模式、开源实现和验证报告的价值，不强行宣布发明成立。

“没有检索到”只能说明本轮证据范围；新颖性、创造性和保护范围须结合申请时的完整资料判断。本阶段只提供可继续检验的技术假设。
