# 无人巡检主场景与介入任务说明

> 阶段：依据文献重选需求的候选稿｜日期：2026-09-29
>
> 用户已确认地图优先、无人巡检为主场景，并要求同时覆盖 Agent 请求参与和用户主动参与；已否定“P1—P5 途中发现围挡”作为核心人工介入需求。本文撤回该设定，推荐“巡检疑点的专家复核与定向补检”。具体行业、岗位和时效要求尚待业务验证，不代表用户已经选定飞机、桥梁或园区业务。
>
> 本文是非规范性研究输入，不是已有系统能力、设备操作规程或实验结果。证据及验证等级见 [07 真实需求依据](07-real-inspection-needs.md)。

具体演练见 [08 双入口任务脚本](08-task-scripts.md)：暂借飞机外观巡检，把“用户主动追加局部检查”和“Agent 请求核实资料差异”写成可逐帧走查的模拟脚本。前者优先，后者明确支持异步，不据此确认航空行业或实时中断必要性。本文仍维护跨设施的场景边界。

## 1. 为什么更换场景

在已知目标和约束内，自主绕障、换路和常规补拍应由系统处理。仅出现围挡、低置信度或计划变化，不能证明需要人。旧场景保留为“不应打扰用户”的对照，不再驱动介入组件设计。

候选业务问题改为：**Agent 请求核查，或用户在巡检执行中主动提出判断、补充要求和调整目标时，如何把人的意图准确关联到资产、证据和实际执行？**

Air-Cobot 论文提供人工追加清单外检查的原型依据；工业巡检专利公开了专家反馈处理链。文献中的机器人协作不等于现代 LLM Agent，也未证明本项目动态界面有优势。

## 2. 候选任务、发起方式与必要性检查

首轮使用单台模拟移动巡检设备、少量具有构件关系的设施资产和可回放图像。资产、缺陷、维修记录及取证时窗均须标为模拟。

候选任务：设备执行例行巡检，专家从回传图像发现清单未覆盖的疑点，结合可追溯的维修背景，提出检查相关构件或另一观察面的需求；系统把这一目标转为已有能力支持的采集任务。证据不足时保留待核验状态，不强迫专家判断正常或故障。

这是从文献推导的设计候选。不能故意屏蔽系统本来能获取的维修记录，也不能关闭自动补拍能力制造人的价值。

### 2.1 两个平等入口

| 发起方式 | 候选触发与例子 | 系统应承接什么 |
| --- | --- | --- |
| Agent 请求参与 | 既有自动核查后，仍需人员解释资料冲突或决定检查范围 | 说明请求理由、证据和等待状态，支持回答、补充或暂不判断 |
| 用户主动参与 | 任务执行正常，检查员新增要求：“把这个构件和相邻部位加入本次复检，原来的例行检查继续。” | 关联所选对象，理解追加目标，检查能力及实际影响并反馈，无须先产生告警 |

后一个例子是交互验证脚本，不是已发生的现场事件。用户可以直接进入 M1 或 M2，不要求先复核疑点再追加检查；Agent 发起同样可以涉及两类任务。发起方式与任务卡是两个不同维度。

用户也可仅查看依据或补充备注。参与不等于暂停、接管或必然改计划；备注仅记录还是作为执行条件，应明确区分。

### 2.2 两类必要性分开判断

下表用于筛选研究场景及判断 Agent 是否值得打扰用户，不能用来限制用户主动表达意图。Agent 主动找人需要可解释的理由；用户主动改变目标不需要先证明异常、低置信度或额外专业知识。请求能否执行仍取决于能力、权限及当前状态。用户明确要求现在调整时，应说明可用处理时机及影响，不因原流程可离线审核就忽略该要求。

| 必要性 | 原型前必须回答的问题 | 不成立时的处理 |
| --- | --- | --- |
| 人提供的增量 | 人带来什么新事实、专业解释或任务目标？能否由已有数据和规则获得？ | 可自动处理的部分不发起征询 |
| 运行中参与 | 决定是否改变离开前应采的证据？结束后处理会增加什么实际成本或失去什么条件？ | 允许巡检后集中审核，不强制暂停 |
| 自主处理边界 | 是否已做适用的自动补拍、历史检索和质量检查？下一步是否已有规则？ | 常规复检继续自动执行 |
| 空间交互 | 是否需要辨认多个资产、关联构件或补查范围？ | 照片足够时不强制地图圈画 |

人员可用性、通信条件、追加出动成本和取证窗口均待访谈确认。注入模拟条件只能证明条件下的机制，不能证明需求普遍存在。

## 3. 角色分工

| 角色 | 职责 |
| --- | --- |
| 专家或检查员 | 指定检查重点、解释资料冲突、提出补证需求；有依据时确认结论，无法判断时请求专项核验 |
| 业务 Agent | 汇聚资产、历史和当前证据；提出有来源的候选补检任务，解释影响并记录实际反馈 |
| 自主执行系统 | 在已有能力与权限内完成路径规划、避障、采集及常规复检；报告执行结果 |
| GUI | 关联证据与具体对象，承接选择、标注和修改；不把人的声明直接显示为已核实事实 |

模拟执行器只回放预设能力，不声称已接入真实机器人或专业缺陷诊断。真实设备的停车和继续由设备控制链决定，不能通过切换界面状态实现。

## 4. 两张候选任务卡

### M1：疑点证据复核

系统请求主要承接 EXP-002，用户主动修改主要承接 EXP-004；纯查看不一律算作打断纠偏。允许异步复核，用户也可主动查看或提出判断；系统是否主动打扰用户另行检验必要性。

1. 将疑点绑定资产和构件，展示当前图像、时间、历史记录及来源，说明已有检查和仍缺什么。
2. 用户可纠正对象关联、提出新的检查问题，或提供有出处的背景资料；不能只有“同意/不同意模型”。
3. 结论允许已解释、需要补证、转专业核验或暂无法判断。专业处置以实际岗位权限和流程为准。
4. 单纯修改注释或复核结果不必进入计划审批；改变采集目标时按 M2 组织执行。

验收：对象和证据关联准确、人的贡献可解释、未解决疑点不会被显示为已排除。成功不等于一定得出缺陷类别。

### M2：追加专项检查与任务影响确认

可由 M1 引出，也可由专家主动发起，不是每个疑点必经的第二个弹窗。

1. 用户指定检查问题、构件或范围；任务正常运行时也可主动追加目标，不要求先有异常或 M1 请求。系统转为实际支持的采集动作，展示不能完成的部分。
2. 导航路径和常规采集参数由执行系统决定。预授权范围内的自动补检无须逐次审批。
3. 专家新提出的任务提交前显示目标与结果要求；只有确实越过业务范围、预算或发生目标冲突时，才增加取舍确认。技术上有影响不等于业务上必须审批。
4. 区分任务已接纳、设备执行中、证据已返回、专家复核完成。补拍成功不等于疑点解决。
5. 保留无关且仍有效的结果；新证据影响到的结论标为待复核，保留历史。不能执行的专项检查显示待人工安排，不伪装成已派单。

预算、时窗与优先级须来自核实流程，未取得前只作显式模拟变量。自由圈画、拖拽重排和暂停恢复按真实需要加入。

## 5. 地图与证据视图的分工

| 视图 | 回答的问题 |
| --- | --- |
| 二维地图或设施平面图 | 资产在哪、有哪些关联设施、哪些区域已检或待补查 |
| 图像及历史对照 | 疑点外观是什么、前后证据是否可比、标注指向哪里 |
| 构件展开图或三维视图（按需） | 位于哪一面、哪个构件，下一观察面如何表达 |

二维地图不能精确代替立面或三维缺陷标注。第一版可用资产选择联动照片；若主要判断只需单张照片，应承认地图仅承担定位。

## 6. 提交与异常分支

提交绑定资产、构件、证据版本、允许操作和相关前置条件。复用现有 ID 与最小校验，不据此引入新平台模型。

| 情况 | 应有行为 |
| --- | --- |
| 取消草稿 | 丢弃本次未提交编辑；已接纳任务不被默默撤销 |
| 相关证据或构件信息变化 | 展示差异并重验决定，不静默替用户改结论 |
| 无关遥测更新 | 不仅因全局版本变化就要求重填 |
| 重复提交或补检 | 检查已有有效任务，防止重复创建和执行 |
| 不支持所需观察面或传感器 | 明示能力缺口，转待专项处理，不假装完成 |
| 人也无法判断 | 保留不确定性和缺失证据，允许退出即时协同 |
| 不支持中途变更 | 排队或重新规划，显示实际影响，不承诺任意位置恢复 |
| 待答请求期间用户另提调整 | 区分新要求与原请求答复，检查同一对象是否冲突，不误填到原请求 |
| 用户查看或记录非执行备注 | 不暂停任务，不把操作记录当成计划变更 |

## 7. 下一步与退出条件

业务路线仍需取得近期真实检查记录或专家走查，核对人工新增了什么信息、为什么需要当时参与，再冻结业务 M1/M2 fixture。暂无业务访问条件时，先按 [08](08-task-scripts.md) 的材料卡和文字故事板开展模拟交互走查；模拟任务已具体化，不等于真实需求已确认。推进步骤见 [05 文献计划](05-literature-plan.md)。

对照包含普通障碍自主处理、规则明确的自动补拍、巡检后集中复核、运行中定向补检。至少分别跑通 Agent 请求、用户发现疑点后主动参与，以及执行正常时用户主动追加检查目标；另测只读查看和两个入口同时存在。记录不必要的打断、证据遗漏、错误关联及重复出动；未获真实设备数据时只报告模拟结果。

若完整自动流程或离线审核同样满足要求，就不把该任务作为实时介入主例；若固定资产面板已足够，就不强行引入动态界面。业务需求和交互困难都成立，才继续检验候选机制。
