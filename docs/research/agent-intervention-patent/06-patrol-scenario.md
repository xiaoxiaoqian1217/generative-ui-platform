# 无人巡检主场景与介入任务说明

> 阶段：场景设计草稿｜日期：2026-09-29
>
> 已确认：以无人巡检为主场景，优先研究地图中的人与 Agent 协同介入。后续迁移验证仍优先选择地图业务。
>
> 以下园区、单台模拟巡检车、P1—P5 巡检点、围挡异常均为本次候选测试设定，不代表已确认的业务需求或项目现有能力。

## 1. 要验证的问题

巡检任务执行中出现变化时，系统怎样让用户看清“哪里出了问题、为什么需要我、允许改什么、改完怎样继续”，并使操作准确关联当前任务。

首版验证交互闭环，不以自动路线规划、多机调度或真实设备控制为前提。是否具备实际业务价值，仍需通过业务访谈或场景评审确认。

## 2. 候选任务与职责

候选任务：巡检车按预设计划检查 P1—P5。P1、P2 已完成；到达 P3 前发现通道围挡。系统只有异常位置和模拟现场画面，不知道施工持续时间。值班人员掌握临时施工通知，因此需要其补充条件并作业务取舍。

| 角色 | 本次职责 |
|---|---|
| 业务 Agent | 维护巡检目标、记录异常、发起协同需求、解释修改影响；仅在预设且校验通过的候选方案中继续 |
| 用户 | 核对现场信息，选择处理方式，必要时声明空间限制、调整未执行任务 |
| GUI 与交互服务 | 将需求组织为地图与介入界面，限制编辑范围，校验提交、显示变更结果；业务合法性由服务端规则确认 |
| 模拟执行器 | 按确定的测试脚本产生状态和回执，用于区分请求接受、步骤执行与任务完成 |

原型可停在模拟等待节点。真实设备是否暂停、能否停在当前位置，必须由控制系统和设备回执确定，不能靠修改界面状态实现。

## 3. 同一异常下的两个介入任务

### M1：异常核查与现场条件补充

对应[技术方案报告 02](02-interaction-model.md)中的“上下文/条件、决策”介入，也作为[推进计划 05](05-literature-plan.md)的首张任务卡。原报告的参数查询例仅作辅助技术解释，不作为主业务驱动。

1. 地图突出 P3 和异常位置，介入卡片显示现场画面时间、发现的围挡、系统缺少的施工信息，以及正在等待处理的任务。
2. 用户核对后补充“该区域本班次封闭”，在预设选项中提出“延期核查 P3”或“继续等待人工核查”的处理选择。涉及巡检点状态或后续安排的修改，在 M2 的影响预览中确认后才生效。选项必须标明适用条件；不能把未接入的人工派单能力伪装成可执行操作。
3. 空间条件先支持选择已有区域；确需表达更准确的施工边界时，再开放当前异常附近的圈画工具。圈画先形成“用户声明的候选约束”，预览后由规则校验坐标、范围和适用时段，通过校验并完成影响预览、由用户确认提交后才能成为任务约束；不等于已核实的现场事实。
4. 提交前展示此次变更及影响：新增哪些条件、P3 将转为什么状态、是否还需调整其他巡检点。超出本次范围的目标或已完成结果不能直接修改。

如果补充条件已足以继续当前预设方案，M1 结束即可，不强制进入 M2，也不强制用户圈画。M1/M2 是验证任务卡，不要求对应两个弹窗；同一允许范围内的条件与计划修改可在一次影响预览后统一确认。

### M2：调整受影响的未执行巡检点

对应报告 02 的“计划”介入，以及计划 05 中的第二张任务卡。当 M1 的条件需要改变巡检点状态或后续安排，或用户主动请求调整未执行项时出现；不要求原计划已经不可执行。

地图展示 P3—P5 与施工区域的关系，列表保留 P1、P2 的完成记录。用户选择需要延期的未执行点，并在预先检查可用性的候选方案中选择后续顺序，例如“P3 延期，继续 P4、P5”。候选方案不是系统已具备自动规划能力的证明。

界面先展示变更对比，再提交。允许延期或调整本次范围内的未执行点；若提出修改任务目标或其他区域，需退出当前编辑并另行确认作用范围。

## 4. 提交与继续执行

每次介入界面绑定任务、目标对象、允许字段与动作、相关状态前置条件及结束条件。前端限制操作，服务端再次校验，不能只靠隐藏按钮约束修改。

合法提交后，系统记录修改：P1、P2 仍有效的既有结果继续保留；P3 延期仍是未完成事项，并保留原因和后续处理责任；只有依赖新条件的后续步骤需要重新检查。

模拟执行从预设的后续入口继续。界面依次区分“变更已接受”“后续步骤执行中”“步骤执行成功”；收到接受回执不代表设备已执行或任务已完成。

所谓局部恢复依赖执行器支持明确等待点、结果有效性检查和恢复入口；不预设所有 Agent 都具备这些能力。

## 5. 必须覆盖的异常分支

| 情况 | 应有行为 |
|---|---|
| 用户取消编辑 | 丢弃本次整份未提交草稿（含合并的 M1/M2），保留提交前的权威状态；先前已接纳的变更不自动撤回，未解决的问题仍待处理 |
| 候选方案或对象变化导致相关前置条件失效 | 旧界面停止接受提交，指出具体变化并提供刷新后的对比；不能静默替用户改选 |
| 无关状态更新 | 例如另一位置收到新遥测，不应仅因全局版本变化就强制用户重填；重检相关前置条件 |
| 圈画越界或修改超范围 | 拒绝回写，指出错误位置和允许范围，保留可修正草稿 |
| 恢复入口不可用 | 明示无法直接继续，提供重新评估或人工处理入口；说明哪些后续步骤需重做，不假装局部恢复成功 |

## 6. 最小实现与验收

先完成 M1 的“发现围挡→补充施工条件或选择等待核查→校验与确认→显示接纳结果”路径；涉及 P3 延期或其他后续调整时，加入 M2 影响预览后才提交该计划修改。空间圈画按需要加入。数据均使用明确标注的模拟输入。

- 用户能从界面指出异常位置、介入原因、可改范围和下一步影响。
- 一次有效操作只改变授权对象；P1、P2 的记录不被覆盖，延期不被计为完成。
- 相同提交重复到达不产生重复变更；已处理界面转为只读记录。
- 相关候选变化导致前置条件失效时旧操作被拒绝；无关更新不无故中断填写。
- 至少跑通取消、越界、候选失效和不支持恢复四类反例。

以上属于原型验收条件，不是已经取得的效果数据。后续先检验主场景是否成立，再选择第二个地图业务验证机制的迁移性。
