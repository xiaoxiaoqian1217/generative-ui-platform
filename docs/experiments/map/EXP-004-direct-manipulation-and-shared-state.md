# EXP-004：用户直接操作 GUI 后，Agent 如何基于最新状态继续

> **实验问题**：当用户不通过自然语言，而是直接在 GUI 中完成选择、调整等具有任务语义的操作后，Agent 是否应该把这些变化作为最新上下文继续工作？  
> **实验目的**：验证“直接操纵也是一种用户输入”，并尝试沉淀“用户直接操作 → 语义状态更新 → Agent 基于最新状态继续”的可复用交互模式、设计原则与适用边界。

---

## 1. 实验目标

EXP-001 验证 Agent 操作界面时，用户能不能理解它正在做什么；EXP-002 验证 Agent 什么时候应该主动把决定交给用户；EXP-003 验证用户通过语言纠偏后，旧计划应该如何失效。

EXP-004 进一步验证一种传统 GUI 中更自然的交互方式：

> **用户不一定会通过聊天告诉 Agent 自己做了什么，而可能直接操作界面。**

例如 Agent 已经在地图中展示了一条候选路线和几个观察点，此时用户直接在地图上选中另一个观察点，然后说：

> **“把这个也纳入路线。”**

对用户来说，“这个”已经通过 GUI 操作表达得很清楚。

但如果 Agent 只能读取聊天文本，就不知道用户刚刚选择了什么。

因此，本实验只验证一个问题：

> **当用户通过直接操纵改变了具有任务语义的 GUI 状态后，这个状态是否应该成为 Agent 后续推理的最新上下文？**

这里重点验证的是**有任务语义的操作状态**，而不是把所有 GUI 行为都同步给 Agent。

---

## 2. 实验场景

继续沿用“北侧通道巡逻方案研判与调整”场景。

用户首先提出：

> **帮我想想怎么巡逻北侧通道。**

Agent 已经完成：

```text
显示限制区域
↓
聚焦北侧通道
↓
高亮观察点 A / B / C
↓
预览候选路线 A
```

此时地图上还存在一个未纳入路线的观察点 D。

用户不通过语言描述“观察点 D”，而是：

```text
在地图上直接点击观察点 D
↓
观察点 D 进入选中状态
↓
用户说：
“把这个也纳入路线。”
```

理想情况下，Agent 能够理解：

```text
“这个”
=
当前 GUI 中用户刚刚选中的观察点 D
```

然后基于最新状态继续：

```text
读取当前选中对象 D
↓
结合当前候选路线 A
↓
重新调整路线
↓
预览路线 B
↓
给出更新后的建议
```

本实验不验证：

- 任意鼠标轨迹是否都应该同步给 Agent；
- 地图每次缩放、拖动是否都属于 Agent 上下文；
- 多人同时操作同一界面的状态合并；
- 通用前端状态同步框架；
- 完整 Collaborative Editing / CRDT。

这些都超出本轮范围。

---

## 3. 对照方案

两种方案保持以下内容一致：

```text
相同初始任务
相同地图数据
相同候选路线 A
相同观察点 D
相同用户点击操作
相同后续语言：
“把这个也纳入路线”
```

唯一改变的是：

> **用户直接操作产生的语义状态，是否会进入 Agent 的最新上下文。**

### 3.1 A0：GUI 状态只停留在前端

```text
Agent 展示候选路线 A
↓
用户点击观察点 D
↓
前端显示 D 已选中
↓
用户：
“把这个也纳入路线。”
↓
Agent 只看到文本
↓
Agent 不知道“这个”指什么
```

此时 Agent 可能：

- 再次询问用户具体是哪一个观察点；
- 错误猜测用户指的是其他对象；
- 忽略用户刚刚完成的 GUI 操作；
- 让用户重复用语言描述界面中已经表达过的信息。

问题在于：

> **用户已经通过 GUI 提供了一次输入，但 Agent 没有把它当作输入。**

### 3.2 A1：语义 GUI 状态进入 Agent 上下文

```text
Agent 展示候选路线 A
↓
用户点击观察点 D
↓
前端更新：selectedObservationPoint = D
↓
该语义状态进入共享上下文
↓
用户：
“把这个也纳入路线。”
↓
Agent 读取最新选择 D
↓
重新调整候选路线
↓
地图展示路线 B
```

这里同步的不是：

```text
mouseX = 813
mouseY = 426
mapZoom = 13.42
```

而是：

```text
selectedObservationPoint = D
```

也就是说，本实验关注的是：

> **把用户直接操纵后的“语义结果”提供给 Agent，而不是把所有底层界面事件都提供给 Agent。**

## 4. 实验结果

> **待实际验证后填写。**

### A0

- 用户是否需要重复描述已经通过 GUI 表达的信息：
- “这个 / 这里 / 这一条”等指代表达是否容易失效：
- Agent 是否容易猜错当前用户关注对象：
- 是否存在某些 GUI 操作其实完全不需要 Agent 知道：

### A1

- 用户是否能够自然地在“直接操作”和“语言”之间切换：
- Agent 是否能正确理解最新选中对象：
- 哪些 GUI 状态值得进入 Agent 上下文：
- 状态同步是否产生多余干扰或错误推理：
- 用户操作后是否需要额外提示 Agent 已感知该状态：

### 当前判断

> 待验证后填写。

实验不预设所有 GUI 状态都应该共享。

如果最终发现只有少量具有任务语义的状态值得同步，那么实验同样达到了目的：明确**哪些状态应该成为 Agent Context，哪些不应该。**

## 5. 最终沉淀

本实验最终需要回答的不是“Shared State 做出来了吗”，而是：

> **当用户通过直接操纵表达意图时，Agent 与 GUI 应该如何共享这个意图，并让协作自然继续？**

### 5.1 Interaction Pattern

如果实验支持 A1，可以形成候选模式：

#### Direct Manipulation as Semantic Input

```text
User Direct Manipulation
↓
Semantic GUI State Update
↓
Agent Reads Latest Shared State
↓
Reconcile with Current Task
↓
Continue
```

含义：

> **用户在 GUI 中完成具有任务语义的直接操作后，系统把操作结果转化为结构化语义状态；Agent 后续基于该状态继续，而不要求用户重新用自然语言描述已经表达过的信息。**

这个模式同样不应该绑定地图。

例如：

```text
地图
用户点击观察点 D
→ selectedLocation = D
→ “把这个也纳入路线”

表格
用户勾选三条记录
→ selectedRows = [...]
→ “比较一下这些设备”

甘特图
用户选择两个冲突任务
→ selectedTasks = [...]
→ “看看怎么调整更合适”

工作流
用户点选失败节点
→ selectedNode = X
→ “从这里继续分析”
```

### 5.2 Design Principle

基于实验，可以形成以下候选原则：

> **当用户通过 GUI 直接操作明确表达了与当前任务相关的对象、范围、选择或调整结果时，应把操作后的语义状态作为 Agent 的最新上下文，而不是要求用户再次通过自然语言重复表达。**

但这并不意味着所有 GUI 状态都应该进入 Agent Context。

更合理的判断是：

```text
这个状态是否表达了用户当前任务意图？
+
Agent 后续是否需要它才能正确继续？
```

如果答案都是“是”，更值得同步。

如果只是：

```text
随手拖动地图
临时缩放
鼠标悬停
纯视觉浏览
```

则通常不应该因为界面发生变化就自动提升为 Agent 的任务上下文。

### 5.3 Boundary

**适合进入 Agent Context：**

- 用户明确选择了对象；
- 用户定义了范围或区域；
- 用户修改了当前方案中的关键参数；
- 用户直接调整了与当前任务相关的结构；
- 后续语言出现“这个 / 这里 / 这些 / 按现在这样”等指代，需要 GUI 状态才能理解。

**通常不需要同步：**

- 普通浏览、平移、缩放；
- Hover 等瞬时视觉状态；
- 与当前任务无关的界面操作；
- Agent 后续推理完全不需要的纯展示状态。

**需要进一步判断：**

如果用户直接操作本身会立即产生业务副作用，例如：

```text
拖动即修改真实排期
点击即下发设备控制
编辑即提交业务数据
```

则问题已经不只是 Shared State，而会涉及：

```text
Authority
Confirm
Commit
Undo / Compensation
```

这些应独立验证。

---

## 6. 下一步

实验结束后根据结果决定下一步：

```text
A0 已经足够
→ 说明该类 GUI 状态不值得同步
→ 收窄 Shared State 范围

A1 明显更自然
→ 固化 Direct Manipulation as Semantic Input
→ 明确哪些状态属于 Agent Context

A1 能工作但状态过多
→ 下一步重点验证 Semantic State Selection
→ 不做全量 GUI State Sync

用户直接操作与 Agent 操作发生冲突
→ 下一步进入“共享 GUI 中谁拥有当前控制权”的实验
```

最终需要回答的是：

> **用户已经通过界面表达过一次的信息，Agent 是否还应该要求用户再说一遍？以及什么样的 GUI 状态才值得成为 Agent 的共同上下文？**
