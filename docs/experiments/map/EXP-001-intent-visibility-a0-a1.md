# EXP-001：Agent 意图可见性——A0 vs A1

> **实验问题**：Agent 连续操作地图时，是否需要向用户展示“当前正在做什么”？  
> **实验目的**：验证最小语义反馈是否有助于用户理解 Agent 对共享 GUI 的连续操作，并尝试沉淀可复用的交互模式、设计原则与适用边界。

---

## 1. 实验目标

当前地图场景已经能够跑通：

```text
用户提出任务
↓
Agent 调用地图工具
↓
地图连续发生变化
↓
Agent 给出最终结果
```

这已经证明 Agent 可以操作地图，但还存在一个交互问题：

> **当地图连续发生变化时，用户是否能理解这些变化为什么发生，以及 Agent 当前正在做什么？**

因此，本实验只验证一个问题：

> **多步 Agent GUI 操作是否需要最小的意图反馈？**

重点不是增加更多过程信息，而是判断：

> **什么程度的反馈已经足以帮助用户理解 Agent 的行为。**

---

## 2. 实验场景

沿用“北侧通道巡逻方案研判与调整”场景。

用户提出：

> **帮我想想怎么巡逻北侧通道。**

Agent 使用固定的地图操作完成方案展示：

```text
显示限制区域
↓
聚焦北侧通道
↓
高亮关键观察点
↓
预览候选路线 A
↓
给出最终建议
```

对应当前地图工具：

```text
setLayerVisibility(...)
↓
focusOn(...)
↓
highlight(...)
↓
previewPath(...)
```

本实验不验证：

- Agent 是否能够正确规划路线；
- Agent 是否能够自主发现工具；
- 业务分析本身是否正确。

这些内容保持固定，使实验只关注**交互反馈方式**。

---

## 3. 对照方案

两种方案保持以下内容一致：

```text
相同任务
相同业务数据
相同 Agent 行为
相同 Tool Call
相同执行顺序
相同地图最终结果
相同最终回答
```

唯一改变的是：

> **Agent 操作地图过程中，是否向用户表达当前意图。**

### 3.1 A0：只展示地图变化和最终结果

当前基线：

```text
用户：
“帮我想想怎么巡逻北侧通道”

↓
地图显示限制区域

↓
地图移动到北侧通道

↓
地图高亮观察点

↓
地图出现候选路线 A

↓
Agent：
“建议采用路线 A……”
```

用户能够看到地图变化，但没有额外说明这些变化的目的。

可能出现的问题：

- 地图为什么突然移动了？
- 为什么这些地方被高亮？
- Agent 现在是在分析，还是已经完成了？

### 3.2 A1：增加最小意图反馈

保持所有地图操作不变，只增加简短的语义反馈：

```text
用户：
“帮我想想怎么巡逻北侧通道”

↓
Agent：
“先看看北侧通道周边的限制条件。”

↓
地图显示限制区域并聚焦北侧通道

↓
Agent：
“再标出几个需要重点关注的位置。”

↓
地图高亮关键观察点

↓
Agent：
“基于这些位置预览一条候选路线。”

↓
地图展示路线 A

↓
Agent：
“建议采用路线 A……”
```

这里展示的不是技术信息：

```text
focusOn(...)
highlight(...)
TOOL_CALL_START
```

而是：

> **Agent 为什么正在改变当前界面。**

## 5. 最终沉淀

实验完成的标准不是“A1 功能开发完成”。

真正需要判断的是：

> **这个实验是否能够增加一条可复用的 Agent–User Interaction 知识。**

### 5.1 Interaction Pattern

如果实验支持 A1，可以形成候选模式：

#### Semantic Intent Feedback

```text
Agent Intent
↓
Semantic Feedback
↓
GUI Change
↓
Continue
```

含义：

> **当 Agent 连续改变共享 GUI 时，在关键状态变化前，用简短的用户语义说明当前操作意图。**

它不应该绑定地图。

例如：

```text
地图
“正在查看北侧限制条件”
→ 地图聚焦

表格
“正在筛选需要重点处理的设备”
→ 表格过滤

甘特图
“正在查看几个时间冲突的任务”
→ 任务高亮

工作流
“正在检查失败节点”
→ 节点定位
```

如果能够脱离 GIS 继续成立，它才有成为可复用 Pattern 的价值。

### 5.2 Design Principle

基于实验，可能形成以下候选原则：

> **当 Agent 主动改变用户当前工作界面，并且变化原因无法仅通过界面本身自然理解时，应提供最小的语义意图反馈。**

这里的重点不是每次 Tool Call 都必须告诉用户，而是判断：

```text
这个变化是否影响用户当前工作上下文？
+
用户能否从 GUI 本身自然理解为什么发生？
```

如果答案是“会影响”且“无法自然理解”，则更值得提供 Intent Feedback。

这条原则需要根据实验结果确认、修改或推翻。

### 5.3 Boundary

即使 Semantic Intent Feedback 成立，也不代表所有 Agent 操作都应该显示过程信息。

**适合：**

- Agent 连续执行多个 GUI 操作；
- Agent 主动改变用户当前工作上下文；
- 单看视觉变化无法自然理解其原因；
- 用户可能需要在过程中判断是否继续。

**可能不需要：**

- 一步即可完成的简单操作；
- 用户已经明确要求某个具体动作；
- GUI 变化本身非常直观；
- 用户只关心最终结果；
- 后台操作不会改变当前工作界面。

例如：

```text
用户：
“定位无人机 01”

Agent：
直接聚焦无人机 01
```

这种操作可能不需要额外显示“正在定位无人机 01”，因为用户本来就知道为什么地图发生变化。

**可能需要更强机制：**

如果操作具有以下特征：

```text
高风险
不可逆
耗时较长
影响范围较大
```

最小语义反馈可能不够。

这时需要验证的可能是：

```text
Preview
Confirm
Progress
Approval
```

而不是继续增加更多 Intent 文本。

---

## 6. 下一步

实验结束后根据结果决定下一步，而不是默认继续增加功能。

```text
A0 已经足够
→ 不增加过程反馈
→ 明确“不需要 Semantic Feedback”的边界

A1 解决了明显问题
→ 固化 Semantic Intent Feedback
→ 提炼 Design Principle 与 Boundary

A1 有帮助但仍不足
→ 判断缺的是视觉反馈、执行状态还是更完整的过程信息
→ 再设计下一轮实验

发现问题并不是“意图不可见”
→ 修改当前判断
→ 不继续堆过程 UI
```

最终要回答的不是：

> **A1 做出来了吗？**

而是：

> **对于 Agent 连续操作共享 GUI，我们多知道了一条什么可复用的交互规律？**
