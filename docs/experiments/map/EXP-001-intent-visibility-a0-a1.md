# EXP-001：Agent 意图可见性 - A0 vs A1

> **实验问题**：Agent 连续操作地图时，用户能否理解变化由谁发起、为什么发生、当前进行到哪里，以及下一步由谁行动？
> **实验目的**：通过一条真实、可运行的地图协作场景，验证当前意图、关键完成事实和结果边界是否形成自然、可信且不过度打扰的用户体验。

| 项目 | 当前状态 |
| --- | --- |
| Research Question | RQ4：Agent 的意图和动作需要多大程度可见？ |
| Hypothesis | H4：多步 Agent 操作至少需要“当前意图 + 关键结果”的最小语义反馈。 |
| 母场景 | 北侧通道巡逻方案研判与调整。 |
| 核心场景 | 场景 A：多步工具中介。 |
| 横切维度 | F：意图可见性。 |
| Web 验证场景 | Workbench 快捷场景“北侧通道巡逻方案”。 |
| 工程状态 | 当前参考体验已经实现并通过自动化回归。 |
| 实验状态 | E1 工程证据已具备，形成性体验观察待完成。 |
| 当前可声称内容 | 该机制可以在真实 AG-UI、Frontend Tool 和 MapLibre 链路中稳定运行。 |
| 当前不可声称内容 | 当前反馈已经提高目标用户的理解、归因或控制感。 |

文件名和标题中的 `A0 vs A1` 保留为实验演进的历史标识，避免破坏现有引用。
它不表示 Workbench 需要提供 A0/A1 切换、并排展示或实验模式。

## 1. 实验目标

当前地图场景已经能够跑通：

```text
用户提出任务
-> Agent 调用地图工具
-> 地图连续发生变化
-> Agent 给出最终结果
```

这已经证明 Agent 可以操作地图，但还没有回答：

> **用户能否理解地图为什么变化、变化由谁发起，以及 Agent 当前正在做什么？**

因此 EXP-001 关注的是连续地图操作中的意图可见性，而不是继续增加地图能力。
它对应的研究和工程关系为：

```text
母场景：北侧通道巡逻方案研判与调整
  -> 核心场景 A：Agent 多步操作共享地图
    -> 横切维度 F：用户能否理解变化的发起者与原因
      -> EXP-001：连续地图操作中的意图可见性
        -> Web 验证场景：北侧通道巡逻方案
```

EXP-001 不是一个独立业务场景，也不是需要交付给用户的实验产品。
用户最终体验的是一条自然、完整的 Agent 地图协作流程。

## 2. 实验场景

沿用“北侧通道巡逻方案研判与调整”场景。

用户提出：

> **帮我想想怎么巡逻北侧通道。**

场景使用固定的任务区域、观察点、限制区和候选路线。
Agent 不负责生成新的专业路线或业务事实。

Agent 使用固定地图操作完成方案展示：

```text
显示任务限制图层
-> 聚焦北侧通道
-> 标记观察点和限制区
-> 临时预览候选路线 A
-> 给出当前结果和决策边界
```

对应当前地图工具：

```text
setLayerVisibility(...)
-> focusOn(...)
-> highlight(...)
-> previewPath(...)
```

本实验验证：

- 用户是否知道地图变化由 Agent 发起；
- 用户是否理解每次变化服务于什么任务目的；
- 用户是否能够恢复 Agent 已完成的关键工作；
- 用户是否知道路线 A 只是临时预览；
- 用户是否知道最终路线尚未比较、选择或提交；
- 当前反馈是否重复、遮挡或打断地图观察。

本实验不验证：

- Agent 是否能够正确规划路线；
- Agent 是否能够自主发现地图工具；
- 真实 LLM 是否能够稳定选择正确的工具和顺序；
- 路线 A 与路线 B 的业务优劣；
- 用户选择、取消或修改路线的 Human-in-the-loop 闭环；
- 打断、纠偏、直接操纵和控制权让渡。

路线选择和修改属于场景 B。
真实 LLM 的自主工具选择由 `map-validation-agent` 的版本化场景单独验证。

## 3. 对照方案

A0 和 A1 用于记录问题如何被发现以及当前设计如何演进。
它们不是当前 Web 界面需要暴露的两个产品模式。

### 3.1 A0：历史工程基线

Issue #214 已经证明 Agent 可以在同一个 MapLibre Surface 上连续执行四个地图域意图。
用户能够看到地图变化和最终结果，但默认界面没有持续表达每次变化的任务目的。

这条基线可能产生的问题包括：

- 地图为什么突然移动；
- 为什么这些位置被高亮；
- 当前是在分析、预览还是已经完成；
- 路线是否已经选定；
- 下一步应该由谁行动。

A0 的作用是说明意图可见性问题从哪里产生。
它不需要作为当前 Workbench 中可切换的体验继续保留。

### 3.2 A1：当前参考体验

当前工程已经在正常 Conversation 和 Map Workspace 中提供：

```text
公开当前研判目标
-> 执行对应地图变化
-> 呈现已经完成的关键事实
-> 标记候选路线只是临时预览
-> 明确尚未完成最终方案选择
```

这里展示的是 Agent 为什么正在改变当前界面，而不是 `TOOL_CALL_START`、`focusOn()` 或参数 JSON。

A1 是历史设计名称。
在当前项目中，它表示唯一需要继续验证和改进的 Web 参考体验，而不是一个可选展示模式。

### 3.3 Web 呈现边界

Workbench 不提供：

- A0/A1 并排展示；
- A0/A1 一键切换；
- 面向用户的实验版本标签；
- 独立实验页面；
- 可视化 Pattern Card；
- 交互模式展示墙。

如果后续需要追溯历史版本，应使用提交、录屏、截图和 Inspect 证据，而不是把实验控制项带入当前 Web 体验。

### 4.2 当前用户感知契约

Workbench 只投影 Agent 已公开的计划、真实 Tool Call、Tool Result 和地图状态。
Workbench 不生成私有推理，不提前显示尚未发生的操作，也不补写事件中不存在的分析理由。

当前动作贴近 Map Workspace 呈现，使用户能够把语义和正在发生的地图变化联系起来。
已经完成的关键事实进入 Conversation，使用户离开当前地图视图后仍能恢复任务语境。

`previewPath` 只表示临时预览既有路线。
界面不得声称路线已经计算、优化、比较、选定或提交。

原始事件、关联标识、工具参数和完整结果进入 Inspect。
默认 Conversation 和 Map Workspace 不承担协议日志展示职责。

## 5. 实验执行方案

### 5.1 验证方式

验证直接发生在正常的“北侧通道巡逻方案”Web 场景中。
参与者体验当前唯一的参考流程，不选择实验版本，也不操作对照开关。
观察者不在任务过程中解释界面设计意图。

当前只有开发者本人时，可以先执行形成性自测，发现明显问题并保留反例。
具备接近目标角色的参与者后，应使用同一场景复验。
单次自测不得被表述为普遍用户结论。

### 5.2 任务后问题

参与者在不打开 Inspect 的情况下回答：

1. 地图变化由谁发起？
2. Agent 依次完成了哪些工作？
3. 为什么地图会显示限制区、高亮观察点并出现路线 A？
4. 路线 A 是否已经被最终选定？
5. 下一步应该由 Agent 继续行动，还是由用户决定？
6. 哪些信息有帮助、重复、干扰或缺失？

观察者同时记录参与者是否主动追问“发生了什么”或“为什么这样变化”。

### 5.3 观察维度

| 维度 | 支持当前设计的现象 | 反驳或限制当前设计的现象 |
| --- | --- | --- |
| 操作归因 | 参与者能够判断地图变化由 Agent 发起。 | 参与者把 Agent 操作误认为系统自动变化或自己的操作。 |
| 任务关系 | 参与者能够说明限制、聚焦、高亮和预览之间的任务关系。 | 参与者只记住文字或最终路线，无法理解操作关系。 |
| 结果边界 | 参与者知道路线 A 只是临时预览，尚未最终选择。 | 参与者误以为路线已经选定、提交或开始执行。 |
| 下一行动者 | 参与者知道下一步需要比较、调整或由自己决定。 | 参与者不知道任务是否完成，也不知道谁应该继续行动。 |
| 信息负担 | 信息能够被注意，并且没有明显打断地图观察。 | 信息重复地图内容、遮挡目标、消失过快或产生不必要的等待感。 |

本实验不使用缺乏研究设计依据的人为通过率制造伪精确结论。
结果应同时报告任务表现、参与者解释、反例和样本局限。

### 5.4 证据包

每次形成性验证至少保留：

- 提交、配置、Agent source 和场景标识；
- 屏幕录制或关键步骤截图；
- Inspect 中的公开 AG-UI 事件、Tool Call 和 Tool Result；
- 地图操作前后状态；
- 参与者逐题回答和观察记录；
- 误解、追问、干扰和反例；
- 从原始证据到最终判断的追溯关系。

## 7. 最终沉淀

EXP-001 的核心成果不是一段孤立思想、Pattern Card 或对照实验界面。
它最终应沿两个维度形成一个可追溯的知识包：

```text
交互知识资产
  - 真实 Web 参考体验
  - 可观察的体验证据与反例
  - 经过验证的交互判断和适用边界

可复用技术资产
  - 支撑参考体验的实现
  - 可重复执行的验证与回归测试
```

### 7.1 交互知识资产

交互知识资产回答“为什么这样设计、在什么情况下适用”。
它由 Web 参考体验、验证记录、候选交互判断和适用边界共同组成。

#### 7.1.1 Web 参考体验

“北侧通道巡逻方案”是当前知识的主要可视化载体。
它应直接体现最终推荐的 Agent 地图协作方式，而不是向用户解释研究过程。

#### 7.1.2 验证记录

本文记录验证问题、工程事实、体验证据、反例、结论和局限。
当体验发生调整时，结论必须能够追溯到具体运行和观察证据。

#### 7.1.3 候选交互判断

当前候选判断是：

> 当 Agent 连续改变共享 GUI，并且用户无法仅从界面变化理解原因时，界面应在变化附近提供最小的公开意图、关键完成事实和结果边界。

这条判断仍需体验证据支持、修改或推翻。
当前沉淀的是经过实验验证的候选交互模式知识，而不是已经成立的跨领域通用模式。
即使它在地图场景中成立，也不能直接声称已经跨领域复用。

#### 7.1.4 适用边界

当前判断可能适用于：

- Agent 连续执行多个可见 GUI 操作；
- 操作会改变用户当前工作上下文；
- 单看视觉变化难以理解原因；
- 用户可能需要在过程中判断是否继续或接管。

当前判断可能不适用于：

- 一步即可完成且意图明确的操作；
- 用户已经明确要求某个具体界面动作；
- 不改变当前工作界面的后台任务；
- 用户只需要最终结果且过程不会影响决策的任务。

高风险、不可逆、耗时或影响范围大的操作需要单独验证 Preview、Confirm、Progress 或 Approval，而不是继续增加意图文本。

### 7.2 可复用技术资产

可复用技术资产回答“如何实现并持续验证”。

当前可复用技术资产包括：

- 地图域意图工具及其结果契约；
- 公开计划与真实地图操作的用户语义投影；
- 当前动作、关键结果和决策边界的 Web 呈现；
- 确定性场景 fixture；
- 单元测试、协议场景测试和浏览器 E2E。

这些能力继续保留在 `web-workbench` 和现有 packages 中。
它们当前可以在本项目和相近地图场景中直接复用，并具备被其他项目采用的技术基础。
这不表示它们已经被提取为可安装到任意项目的通用 package。

### 7.3 两类成果的关系与抽象边界

交互知识资产提供设计依据，技术资产承载实现和持续验证。
真实 Web 参考体验和验证证据将两者连接起来，使交互判断能够追溯到具体实现和观察结果。

没有第二个真实消费者之前，不为 EXP-001 新建通用交互模式 package 或实验平台。
出现第二个真实 GUI 场景后，再根据复验结果识别稳定部分、领域特有部分和合理的公共抽象边界。
