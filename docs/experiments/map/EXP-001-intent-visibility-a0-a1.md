# EXP-001：Agent 操作地图时，需要展示多少过程信息？

> **实验目标**：验证 Agent 连续操作地图时，是否需要向用户展示“当前正在做什么”，以及最小反馈做到什么程度比较合适。  
> **结论边界**：本实验用于发现明显交互问题、比较 A0 / A1 的体验差异，并形成初步交互设计判断；结论只覆盖当前场景和当前验证条件，不直接扩展为普遍用户结论。

---

## 1. 为什么做这个实验

当前地图场景已经能够跑通：

```text
用户提出任务
↓
Agent 调用地图工具
↓
地图连续发生变化
↓
Agent 给出最终结果
```

工程上已经证明：

> Agent 可以连续操作一个共享地图界面。

但还没有回答：

> **用户是否知道地图为什么发生变化，以及这些变化是不是 Agent 主动做的？**

例如 Agent 连续执行：

```text
显示限制区域
↓
聚焦北侧通道
↓
高亮观察点
↓
预览路线 A
```

如果界面只是不断变化，最后再给一句总结，用户可能知道最终结果，却不知道中间每一步为什么发生。

因此 EXP-001 只验证一个问题：

> **多步 Agent 操作是否需要过程中的最小意图反馈？**

---

## 2. 怎么验证

使用完全相同的任务和 Agent 操作，只改变用户看到的过程反馈。

固定内容：

```text
相同任务
相同业务数据
相同 Agent 行为
相同 Tool Call
相同执行顺序
相同地图最终状态
相同最终回答
```

只比较两种交互方式。

这样可以尽量把体验差异归因到“是否展示最小意图反馈”，而不是业务结果或 Agent 行为不同。

---

## 3. A0：只展示地图变化和最终结果

当前基线：

```text
用户：
“帮我想想怎么巡逻北侧通道”

↓
地图打开限制区域

↓
地图移动到北侧通道

↓
地图高亮观察点

↓
地图出现候选路线

↓
Agent：
“建议采用路线 A……”
```

用户可以看到结果，但界面没有明确说明：

- 为什么突然移动地图；
- 为什么打开这个图层；
- 为什么高亮这些位置；
- 当前 Agent 做到了哪一步。

---

## 4. A1：增加最小意图反馈

Agent 操作地图时增加一句很短的语义反馈。

例如：

```text
正在查看北侧通道及周边限制条件
↓
地图显示限制区域并聚焦北侧通道

正在标出需要重点关注的位置
↓
地图高亮观察点

正在预览候选巡逻路线
↓
地图展示路线 A

已完成方案展示
↓
Agent 给出最终建议
```

这里展示的不是：

```text
focusOn()
highlight()
previewPath()
TOOL_CALL_START
```

而是用户真正关心的：

> **Agent 为什么正在改变当前界面。**

---

## 5. 主要观察什么

本实验不设置“理解率达到多少才算成功”之类硬指标，优先观察实际现象和反例。

| 观察点 | 想知道什么 |
| --- | --- |
| 地图变化时是否知道为什么变化 | Agent 意图是否清晰 |
| 是否知道变化由 Agent 发起 | 操作归因是否清晰 |
| 有没有某一步感觉突然或莫名其妙 | A0 的问题具体在哪里 |
| A1 的文字是否真正有帮助 | 最小反馈是否有效 |
| 有没有提示没有看的必要 | 是否反馈过多 |
| 是否真正需要地图视觉反馈而不是文字 | 当前假设是否错误 |

必要时保留：

- Tool Call / Tool Result；
- 操作录屏或截图；
- 当时的观察记录；
- 明显失败案例与反例。

---

## 6. 为什么这种验证可信

### 6.1 只改变一个核心变量

```text
任务不变
Agent 行为不变
地图结果不变
只改变反馈方式
```

因此如果 A0 / A1 出现明显体验差异，更容易判断差异来自交互反馈本身。

### 6.2 验证发生在真实交互链路中

不是只看静态原型，而是在实际链路中观察：

```text
Agent 请求
→ Tool Call
→ 前端执行
→ 地图状态变化
→ Tool Result
→ Agent 继续
```

因此验证的是 Agent 与 GUI 真正协作时发生的问题。

### 6.3 不只寻找支持 A1 的证据

如果出现以下情况，同样要记录：

- A0 已经足够自然；
- A1 基本没有被关注；
- A1 反而增加干扰；
- 真正有帮助的是地图动画或视觉标记，而不是文字；
- 某一步需要反馈，另一些步骤完全不需要。

实验的目标不是证明 A1 一定更好，而是找出什么设计更合理，以及它的适用条件。

---

## 7. 实验可能产生的结果

### 情况 A：A0 已经足够

如果地图变化本身很自然，整个过程都能直接理解：

> 不增加额外过程反馈。

这说明简单或高度可理解的操作不值得增加额外 UI。

### 情况 B：A1 明显有帮助

如果 A0 中容易不知道为什么发生变化，而 A1 能自然地解释整个过程，可以形成一个候选交互模式：

```text
Agent Intent
↓
Semantic Feedback
↓
GUI Change
↓
Continue
```

即：

> **Agent 连续改变共享 GUI 时，在关键状态变化附近提供最小意图反馈。**

### 情况 C：A1 仍然不够

此时不直接增加更多文字，而是继续判断：

```text
需要更明确的地图视觉反馈？
需要区分“正在执行”和“执行完成”？
需要持久过程记录？
还是根本不需要过程信息？
```

再决定下一轮实验。

---

## 8. 最终希望沉淀什么

EXP-001 的价值不是完成一个“A1 功能”，而是尝试形成三个层次的可复用成果。

### 8.1 Interaction Pattern

候选模式：

```text
Agent Intent
→ Semantic Feedback
→ GUI Change
→ Continue
```

### 8.2 Design Principle

候选原则：

> **当 Agent 连续改变用户当前工作界面，并且变化原因不能从界面本身自然理解时，应提供最小的意图反馈。**

该原则需要由实验结果决定是否成立或调整。

### 8.3 Boundary

可能适合：

- Agent 连续执行多个界面操作；
- 界面变化会改变用户当前工作上下文；
- 单看视觉变化难以理解原因。

可能没必要：

- 一步操作即可完成；
- 变化结果本身非常明显；
- 过程反馈比操作本身更打扰；
- 用户只需要最终结果。

最终 Pattern 只有同时记录“什么时候适合”和“什么时候不适合”才具备复用价值。

## 9. 本次只需要实现什么

为了完成 EXP-001，只需要：

```text
现有 A0
+
A1 最小意图反馈
+
A0 / A1 切换
+
复用现有 Tool / Inspector 记录
```

暂时不做：

- A2 完整过程 Timeline；
- Interrupt；
- Undo / Rollback；
- HITL；
- 路线编辑；
- Dynamic A2UI；
- 新地图工具；
- 通用 Interaction Framework。

因为这些能力不会帮助 EXP-001 更清楚地回答当前问题。
