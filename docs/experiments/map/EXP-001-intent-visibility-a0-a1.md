# EXP-001：连续地图操作中的 Agent 意图可见性

> **验证问题**：当 Agent 连续改变共享地图时，用户能否理解变化由谁发起、为什么发生、当前进行到哪里，以及下一步由谁行动？
> **验证目的**：通过一条真实、可运行的地图协作场景，验证当前意图、关键完成事实和结果边界是否形成自然、可信且不过度打扰的用户体验。

## 2. 历史问题与当前方向

### 2.1 历史基线

Issue #214 已经证明 Agent 可以在同一个 MapLibre Surface 上连续执行地图操作：

```text
用户提出任务
-> Agent 调用地图工具
-> 地图连续发生变化
-> Agent 给出最终结果
```

这条基线证明了工程链路可以运行，但没有证明用户能够理解中间发生的变化。
用户可能只看到地图终态，无法恢复动作顺序、变化来源和当前决策阶段。

历史设计讨论将这种仅依赖地图变化和最终回答的状态称为 A0。

### 2.2 当前参考体验

当前工程已经在真实 Conversation 和 Map Workspace 中增加最小语义反馈：

```text
用户提出巡逻任务
-> Agent 公开当前研判目标
-> 地图显示限制条件并聚焦北侧通道
-> 界面呈现已经确认的观察点和限制区
-> 地图临时预览候选路线 A
-> 界面明确尚未比较其他路线，也未完成最终选择
```

历史设计讨论将这种呈现称为 A1。
在当前项目中，它不是可选择的展示模式，而是需要通过真实体验继续验证和改进的唯一参考实现。

### 2.3 不再建设的内容

本实验不建设：

- A0/A1 并排展示；
- A0/A1 一键切换；
- 独立的实验 Web 页面；
- 面向用户的实验版本标签；
- 可视化 Pattern Card；
- 交互模式展示墙；
- 通用实验或交互模式平台。

如果后续研究确实需要历史版本证据，应通过提交、录屏、截图和 Inspect 记录追溯，而不是把实验控制项带入当前 Web 体验。

## 3. Web 验证场景

### 3.1 用户任务

Workbench 中的快捷场景名称为“北侧通道巡逻方案”。
用户也可以直接输入：

> **帮我想想怎么巡逻北侧通道。**

### 3.2 固定业务事实

场景沿用版本化的“北侧通道巡逻方案研判与调整”fixture。
任务区域、观察点、限制区和候选路线都由受控场景提供。
Agent 不负责生成新的专业路线或业务事实。

### 3.3 地图操作链路

场景固定执行：

```text
setLayerVisibility(...)
-> focusOn(...)
-> highlight(...)
-> previewPath(...)
```

对应的用户可见变化为：

```text
显示任务限制图层
-> 聚焦北侧通道
-> 标记观察点和限制区
-> 临时预览候选路线 A
```

### 3.4 验证范围

EXP-001 验证：

- 用户是否知道地图变化由 Agent 发起；
- 用户是否理解每次变化服务于什么任务目的；
- 用户是否能够恢复 Agent 已经完成的关键工作；
- 用户是否知道路线 A 只是临时预览；
- 用户是否知道最终路线尚未比较、选择或提交；
- 当前反馈是否重复、遮挡或打断地图观察。

EXP-001 不验证：

- Agent 是否能够正确规划路线；
- Agent 是否能够自主发现地图工具；
- 真实 LLM 是否能够稳定选择正确的工具和顺序；
- 路线 A 与路线 B 的业务优劣；
- 用户选择、取消或修改路线的 Human-in-the-loop 闭环；
- 打断、纠偏、直接操纵和控制权让渡。

路线选择和修改属于场景 B。
真实 LLM 的自主工具选择由 `map-validation-agent` 的版本化场景单独验证。

## 4. 当前用户感知契约

当前参考体验遵循以下约束。

### 4.1 公开当前意图

地图发生关键变化时，界面使用用户能够理解的任务语言说明当前动作。
界面不显示 `TOOL_CALL_START`、`focusOn()` 或参数 JSON 等协议和实现细节。

### 4.2 只呈现已经公开或已经发生的事实

Workbench 只投影 Agent 已公开的计划、真实 Tool Call、Tool Result 和地图状态。
Workbench 不生成私有推理，不提前显示尚未发生的操作，也不补写事件中不存在的分析理由。

### 4.3 区分当前动作与关键结果

当前动作贴近 Map Workspace 呈现，使用户能够把语义和正在发生的地图变化联系起来。
已经完成的关键事实进入 Conversation，使用户离开当前地图视图后仍能恢复任务语境。

### 4.4 明确结果边界

`previewPath` 只表示临时预览既有路线。
界面不得声称路线已经计算、优化、比较、选定或提交。
场景完成时必须明确下一步仍需要比较、调整或由用户决定。

### 4.5 保留工程审计入口

原始事件、关联标识、工具参数和完整结果进入 Inspect。
默认 Conversation 和 Map Workspace 不承担协议日志展示职责。

## 6. 形成性体验验证

### 6.1 验证方式

验证直接发生在正常的“北侧通道巡逻方案”Web 场景中。
参与者体验当前唯一的参考流程，不选择实验版本，也不操作对照开关。
观察者不在任务过程中解释界面设计意图。

当前只有开发者本人时，可以先执行形成性自测，发现明显问题并保留反例。
具备接近目标角色的参与者后，应使用同一场景复验。
单次自测不得被表述为普遍用户结论。

### 6.2 任务后问题

参与者在不打开 Inspect 的情况下回答：

1. 地图变化由谁发起？
2. Agent 依次完成了哪些工作？
3. 为什么地图会显示限制区、高亮观察点并出现路线 A？
4. 路线 A 是否已经被最终选定？
5. 下一步应该由 Agent 继续行动，还是由用户决定？
6. 哪些信息有帮助、重复、干扰或缺失？

观察者同时记录参与者是否主动追问“发生了什么”或“为什么这样变化”。

### 6.3 观察维度

| 维度 | 支持当前设计的现象 | 反驳或限制当前设计的现象 |
| --- | --- | --- |
| 操作归因 | 参与者能够判断地图变化由 Agent 发起。 | 参与者把 Agent 操作误认为系统自动变化或自己的操作。 |
| 任务关系 | 参与者能够说明限制、聚焦、高亮和预览之间的任务关系。 | 参与者只记住文字或最终路线，无法理解操作关系。 |
| 结果边界 | 参与者知道路线 A 只是临时预览，尚未最终选择。 | 参与者误以为路线已经选定、提交或开始执行。 |
| 下一行动者 | 参与者知道下一步需要比较、调整或由自己决定。 | 参与者不知道任务是否完成，也不知道谁应该继续行动。 |
| 信息负担 | 信息能够被注意，并且没有明显打断地图观察。 | 信息重复地图内容、遮挡目标、消失过快或产生不必要的等待感。 |

本验证不使用缺乏研究设计依据的人为通过率制造伪精确结论。
结果应同时报告任务表现、参与者解释、反例和样本局限。

### 6.4 证据包

每次形成性验证至少保留：

- 提交、配置、Agent source 和场景标识；
- 屏幕录制或关键步骤截图；
- Inspect 中的公开 AG-UI 事件、Tool Call 和 Tool Result；
- 地图操作前后状态；
- 参与者逐题回答和观察记录；
- 误解、追问、干扰和反例；
- 从原始证据到最终判断的追溯关系。

## 8. 最终沉淀

EXP-001 的核心成果不是一段孤立思想、Pattern Card 或对照实验界面。
它最终应形成一个可追溯的知识包：

```text
真实 Web 参考体验
+
可观察的体验证据与反例
+
经过验证的交互判断和适用边界
+
支撑该体验的实现与回归测试
```

### 8.1 Web 参考体验

“北侧通道巡逻方案”是当前知识的主要可视化载体。
它应直接体现最终推荐的 Agent 地图协作方式，而不是向用户解释研究过程。

### 8.2 验证记录

本文记录验证问题、工程事实、体验证据、反例、结论和局限。
当体验发生调整时，结论必须能够追溯到具体运行和观察证据。

### 8.3 技术资产

当前可复用技术资产包括：

- 地图域意图工具及其结果契约；
- 公开计划与真实地图操作的用户语义投影；
- 当前动作、关键结果和决策边界的 Web 呈现；
- 确定性场景 fixture；
- 单元测试、协议场景测试和浏览器 E2E。

这些能力继续保留在 `web-workbench` 和现有 packages 中。
没有第二个真实消费者之前，不为 EXP-001 新建通用交互模式 package 或实验平台。

### 8.4 待验证的交互判断

当前候选判断是：

> 当 Agent 连续改变共享 GUI，并且用户无法仅从界面变化理解原因时，界面应在变化附近提供最小的公开意图、关键完成事实和结果边界。

这条判断仍需体验证据支持、修改或推翻。
即使它在地图场景中成立，也不能直接声称已经跨领域复用。

### 8.5 适用边界

当前判断可能适用于：

- Agent 连续执行多个可见 GUI 操作；
- 操作会改变用户当前工作上下文；
- 单看视觉变化难以理解原因；
- 用户可能需要在过程中判断是否继续或接管。

当前判断可能不适用于：

- 一步即可完成且意图明确的操作；
- 用户已经明确要求某个具体界面动作；
- 不改变当前工作界面的后台任务；
- 用户只需要最终结果且过程不会影响决策的任务。

高风险、不可逆、耗时或影响范围大的操作需要单独验证 Preview、Confirm、Progress 或 Approval，而不是继续增加意图文本。
