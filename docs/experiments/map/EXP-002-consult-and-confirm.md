# EXP-002：Agent 什么时候应该停下来，把决定交给用户？

> **实验问题**：当 Agent 在连续操作共享 GUI 的过程中遇到需要做选择的节点时，应该直接替用户决定，还是停下来征询用户？  
> **实验目的**：验证“Agent 主动执行”与“Agent 在关键决策点让渡控制权”的边界，并尝试沉淀可复用的交互模式、设计原则与适用边界。

---

## 1. 实验目标

EXP-001 关注的是：

> 用户能不能理解 Agent 正在做什么。

EXP-002 进一步关注：

> **即使用户理解 Agent 正在做什么，Agent 是否应该继续替用户做决定？**

在真实 GUI 中，Agent 的操作并不都是同一种性质。

有些动作只是帮助用户观察信息，例如：

```text
聚焦区域
显示图层
高亮对象
```

这类动作通常风险较低，也容易撤销。

但当 Agent 已经完成信息收集，接下来需要在多个合理方案之间做选择时，问题会发生变化：

> **这个选择究竟属于 Agent，还是应该交给用户？**

因此本实验只验证一个问题：

> **当后续动作会表达用户偏好或改变任务方向，而当前上下文不足以确定唯一答案时，Agent 是否应该停下来征询用户？**

---

## 2. 实验场景

继续沿用“北侧通道巡逻方案研判与调整”场景。

用户提出：

> **帮我想想怎么巡逻北侧通道。**

Agent 首先完成相同的信息准备：

```text
显示限制区域
↓
聚焦北侧通道
↓
高亮关键观察点
↓
发现存在两个可行候选路线
```

候选路线由固定 fixture 提供：

```text
路线 A
更短，经过限制区附近

路线 B
更绕，但距离限制区域更远
```

这里不存在一个完全由系统事实决定的唯一答案。

真正需要决定的是：

> **更偏向效率，还是更偏向避开限制区域？**

这使它成为一个明确的“控制权交接点”。

本实验不验证：

- Agent 是否能够自己生成路线；
- 路径规划算法是否正确；
- 哪条路线在业务上绝对更优；
- 高风险操作审批。

候选路线和差异保持固定，只关注 **Agent 是否应该在这里把决定交给用户**。

---

## 3. 对照方案

两种方案保持以下内容一致：

```text
相同用户任务
相同业务数据
相同限制区域
相同观察点
相同候选路线 A / B
相同前置地图操作
```

唯一改变的是：

> **当 Agent 到达存在多个合理选择的节点时，是直接继续，还是停下来让用户决定。**

### 3.1 A0：Agent 直接选择并继续执行

```text
用户：
“帮我想想怎么巡逻北侧通道”

↓
Agent 显示限制区域
↓
Agent 聚焦北侧通道
↓
Agent 高亮关键观察点
↓
Agent 判断路线 A 更合适
↓
地图直接预览路线 A
↓
Agent 给出最终建议
```

这种方式的优点是流程连续、操作少。

但可能产生的问题是：

- Agent 为什么选择 A？
- 用户是否认可 Agent 默认采用的偏好？
- 如果用户实际上更在意避开限制区域，是否需要事后纠正？
- Agent 是否在没有足够依据时替用户做了决定？

### 3.2 A1：Agent 到达决策点后征询用户

前面的地图操作完全相同。

当 Agent 发现路线 A / B 都可行，但取舍取决于用户偏好时，停止继续执行：

```text
Agent：
“目前有两条可行路线：
A 更短，但更靠近限制区域；
B 更绕，但与限制区域保持更大距离。
你更偏向效率，还是更偏向稳妥？”

↓
等待用户选择

↓
用户：
“稳妥一点。”

↓
Agent 预览路线 B
↓
继续给出方案建议
```

这里的关键不是增加一个“确认按钮”，而是：

> **Agent 识别到当前决定依赖用户偏好，因此主动让渡控制权。**

## 4. 实验结果

> **当前状态（2026-08-25）**：A1 的确定性工程闭环已经实现并通过自动化回归，但 EXP-002 尚未完成真实模型与参与者体验验证。

当前工程已经具备以下证据：

- AGUIMock 通过 `requestPatrolRouteSelection` 提供固定路线 A / B，并等待标准 `role = tool` 的用户答复；
- Workbench 通过 `useHumanInTheLoop` 呈现路线差异，支持地图本地预览、选择、取消和固定修改要求；
- 用户选择后，Agent 根据真实 Tool Result continuation 预览对应的既有路线，并明确路线尚未提交或执行；
- Chromium E2E 已验证场景 A 的地图上下文可以保留到征询场景，并覆盖路线 A、路线 B、取消和修改分支；
- Map Validation Agent 已提供正常顺序和候选顺序反转的版本化征询场景，但真实 provider smoke 记录仍为 Pending。

对应工程证据见 [`consult-patrol-route-selection.ts`](../../../packages/ag-ui-mock/src/scenarios/consult-patrol-route-selection.ts)、[`CopilotKitFrontendToolsBridge.vue`](../../../apps/web-workbench/src/conversation/CopilotKitFrontendToolsBridge.vue)、[`workbench.spec.ts`](../../../apps/web-workbench/tests/e2e/workbench.spec.ts) 和 [`smoke/README.md`](../../../apps/map-validation-agent/smoke/README.md)。

### A0

- Agent 直接选择是否自然：待参与者验证。
  A0 是用于比较“Agent 直接替用户选择”的研究对照，不是当前参考体验必须实现的产品能力。
- 是否产生“为什么替我决定”的感觉：待参与者验证。
  只有后续确实执行 A0 对照验证时，才需要补充对应观察记录。
- 是否出现事后纠正：待参与者验证。
  当前自动化不用于证明用户是否会因为 A0 而产生纠正行为。
- 哪些情况下直接继续反而更高效：待参与者验证。
  低风险、可逆且不表达用户偏好的地图观察动作已经由现有场景直接执行，但路线偏好选择不属于这类动作。

### A1

- 征询是否出现在合理的时机：工程 fixture 会在两个合理候选且缺少最终偏好时进入征询。
  真实模型能否在单次自然任务中稳定识别该时机，仍待 provider smoke 与重复运行验证。
- 选项和差异是否足以支持用户做决定：当前界面会同时呈现路线 A / B 的摘要，并允许在地图上分别预览。
  这些信息已足以完成工程交互，但是否足以支持真实用户判断仍待参与者验证。
- 是否感觉被无意义地打断：待参与者验证。
  自动化测试只能证明 Agent 确实停止并等待，不能证明等待是否自然或负担是否合理。
- 用户回答后 Agent 是否能够自然继续：工程闭环已经验证。
  路线 A / B 会映射到对应既有路径，取消不会触发地图 continuation，固定修改要求会高亮桥下区域并继续预览路线 B。
  真实模型续接的语言质量和行为稳定性仍待 provider smoke 验证。

### 当前判断

> 当前工程已经实现 EXP-002 的 A1 核心场景：Agent 在路线决策点进入征询等待，由用户选择路线 A 或路线 B，再根据答复继续。

EXP-002 目前属于“A1 工程实现已经完成，体验实验结论待验证”。
A0 只是文档中的研究对照，不是判断 A1 是否实现的前置条件，也不是当前工程缺口。
前置研判场景与征询场景可以在同一 Conversation 中连续运行，并保留地图上下文。
真实 provider smoke、重复运行和参与者观察尚未完成。

实验不预设“征询越多越好”。

如果发现当前选择本身低风险、容易撤销，而且 Agent 默认选择已经足够自然，那么 A0 可能更合理。

相反，如果决定明显依赖用户偏好、授权或任务方向，而 Agent 无法从上下文确定，那么 A1 更可能有价值。

## 5. 最终沉淀

EXP-002 的目标不是完成一个“确认交互”，而是回答：

> **什么样的决策应该由 Agent 自动继续，什么样的决策应该把控制权交给用户？**

### 5.1 Interaction Pattern

如果实验支持 A1，可以形成候选模式：

#### Agent Yield at Decision Point

```text
Agent Explore / Analyze
↓
Decision Point
↓
Surface Options + Trade-off
↓
Yield to User
↓
User Decision
↓
Agent Continue
```

这个模式不绑定地图。

例如：

```text
地图
两条路线都可行
→ 用户选择效率 / 稳妥

表格
两种筛选策略都会排除部分数据
→ 用户选择更严格 / 更宽松

甘特图
两个任务都可以延期
→ 用户决定调整哪一个

工作流
失败节点可以重试或跳过
→ 用户决定处理方式
```

共同点不是 UI 长什么样，而是：

> **Agent 已经把事实整理清楚，但下一步取舍属于用户偏好或决策权。**

### 5.2 Design Principle

基于实验，可能形成以下候选原则：

> **当下一步操作存在多个合理选项，并且选择依赖用户偏好、授权或任务取舍，而不是可由现有事实唯一确定时，Agent 应显式呈现关键差异并让渡控制权。**

这不等于：

> 每个动作都先问用户。

真正需要判断的是：

```text
是否存在多个合理选项？
+
当前上下文能否确定用户真正想要哪一个？
+
这个选择是否会改变后续任务方向？
```

如果存在多个合理选项、无法从上下文确定用户偏好，并且选择会影响后续任务，则更值得 Yield。

### 5.3 Boundary

**适合：**

- 多个方案都合理；
- 选择依赖用户偏好；
- 选择会改变后续任务方向；
- Agent 无法从已有上下文可靠推断；
- 用户之后纠正的成本明显高于当场选择。

**可能不需要：**

- 用户已经明确表达偏好；
- 只有一个合理方案；
- 操作只是低风险、可逆的视觉调整；
- Agent 可以轻易执行后再由用户调整；
- 征询本身比错误选择带来的成本更高。

例如：

```text
用户：
“定位无人机 01”

Agent：
直接定位
```

这里没有真正的决策分叉，不应该为了“人在环”而额外询问。

**可能需要更强机制：**

如果选择不只是偏好问题，而是涉及：

```text
高风险
不可逆
外部执行
权限或责任
```

那么简单的“征询”可能不够，需要进一步验证：

```text
Preview
Confirm
Approval
```

这些属于后续更强控制机制，不在 EXP-002 中展开。

## 6. 下一步

在进入实验结论判断前，先补齐以下证据：

1. 完成 `north-corridor-route-choice-v1` 和 `north-corridor-route-choice-reversed-v1` 的真实 provider smoke，并记录公开 Tool Call、Tool Result、HITL 答复和最终边界；
2. 如果需要正式比较 A0 / A1，再为 A0 保留同任务、同数据、同前置地图操作下的可审查实验材料，但不把 A0 作为产品能力或增加 A0/A1 产品开关；
3. 使用 A0 / A1 完成形成性参与者验证，记录是否自然、是否打断、是否发生纠正以及用户如何解释路线差异；
4. 将原始运行、截图或录屏、Inspect 证据和参与者回答关联到本节结果，避免仅凭工程可运行性得出体验结论。

实验结束后根据结果决定下一步：

```text
A0 更自然
→ 不在此类低风险决策点强制征询
→ 明确 Agent 可以自动继续的边界

A1 明显更合理
→ 固化 Agent Yield at Decision Point
→ 提炼“何时让渡控制权”的设计原则

A1 太频繁、太打断
→ 收紧 Decision Point 的判定条件

发现真正问题不是“是否征询”
而是“用户如何纠正已经做出的决定”
→ 进入下一轮 Interrupt / Correct 实验
```

最终要回答的不是：

> **是否做了一个确认交互？**

而是：

> **Agent 在什么情况下应该继续自主行动，在什么情况下应该主动把决定交回给用户？**
