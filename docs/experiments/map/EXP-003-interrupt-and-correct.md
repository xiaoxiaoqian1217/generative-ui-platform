# EXP-003：用户打断与纠偏——旧计划什么时候应该失效

> **实验问题**：Agent 连续操作共享 GUI 时，如果用户中途修改要求，Agent 是否应该立即停止尚未执行的旧计划，并基于最新用户意图与最新界面状态重新继续？  
> **实验目的**：验证用户主动纠偏时的控制权优先级，并尝试沉淀“用户接管 → 旧计划失效 → 状态对齐 → Agent 重新继续”的可复用交互模式、设计原则与适用边界。

---

## 1. 实验目标

EXP-001 关注用户能否理解 Agent 正在做什么，EXP-002 关注 Agent 什么时候应该主动把决定交给用户。

EXP-003 进一步验证另一种更主动的情况：

> **如果 Agent 还在执行原来的计划，但用户已经改变了要求，谁应该拥有更高优先级？**

例如 Agent 正在生成北侧通道巡逻方案：

```text
显示限制区域
↓
聚焦北侧通道
↓
高亮观察点
↓
预览候选路线 A
↓
给出最终建议
```

执行到一半时，用户补充：

> **“别走北坡，改从东侧绕。”**

此时原来的候选路线 A 已经基于过时条件产生。

本实验只验证一个问题：

> **当用户的新要求改变当前任务约束时，尚未执行的旧 Agent 计划是否应该失效，并从最新状态重新继续？**

重点不是实现复杂的 Undo / Rollback，而是确认**用户纠偏与 Agent 旧计划之间的优先级规则**。

---

## 2. 实验场景

继续沿用“北侧通道巡逻方案研判与调整”场景。

用户首先提出：

> **帮我想想怎么巡逻北侧通道。**

Agent 按固定顺序开始处理：

```text
显示限制区域
↓
聚焦北侧通道
↓
高亮关键观察点
↓
准备预览候选路线 A
```

在路线 A 真正展示之前，用户插入新的要求：

> **别走北坡，改从东侧绕。**

这条新要求会直接影响后续路线选择，因此原来的“继续展示路线 A”已经不再成立。

理想的后续行为是：

```text
收到用户纠偏
↓
停止尚未执行的旧计划
↓
保留仍然有效的地图状态
↓
把“避开北坡、从东侧绕行”作为最新约束
↓
重新生成并预览路线 B
↓
继续给出建议
```

本实验不验证：

- 已完成高风险操作如何回滚；
- 多 Agent 并发修改同一状态；
- 网络中断后的恢复；
- 完整历史版本管理；
- 通用事务或 Command Admission 机制。

这些都超出本轮范围。

---

## 3. 对照方案

两种方案保持以下内容一致：

```text
相同初始任务
相同地图数据
相同初始 Agent 计划
相同用户纠偏内容
相同纠偏发生时机
相同最终目标：避开北坡，从东侧绕行
```

唯一改变的是：

> **用户纠偏发生后，Agent 是否仍继续执行已经过时的旧计划。**

### 3.1 A0：旧计划继续执行

```text
用户：
“帮我想想怎么巡逻北侧通道。”

↓
Agent 显示限制区域
↓
Agent 聚焦北侧通道
↓
Agent 高亮观察点

用户：
“别走北坡，改从东侧绕。”

↓
Agent 仍然继续旧计划
↓
地图先展示路线 A
↓
Agent 再处理用户的新要求
↓
地图改为路线 B
```

这种方式可能产生几个问题：

- 用户已经纠正了 Agent，但界面仍继续执行旧动作；
- 地图短暂出现一个用户已经明确否定的结果；
- 用户不知道自己的纠偏是否已经生效；
- 新旧计划连续改变同一个 GUI，可能造成状态冲突或认知混乱。

### 3.2 A1：用户纠偏使尚未执行的旧计划失效

```text
用户：
“帮我想想怎么巡逻北侧通道。”

↓
Agent 显示限制区域
↓
Agent 聚焦北侧通道
↓
Agent 高亮观察点

用户：
“别走北坡，改从东侧绕。”

↓
停止尚未执行的 previewPath(A)
↓
保留仍然有效的限制区域、视口和观察点
↓
更新任务约束
↓
Agent 基于最新状态重新判断
↓
地图直接预览路线 B
↓
Agent 给出更新后的建议
```

这里的关键不是把所有旧状态全部清空，而是区分：

```text
已经执行且仍然有效的状态
→ 可以保留

尚未执行、且依赖旧条件的计划
→ 应该失效
```

因此 EXP-003 验证的并不是简单的“用户一说话就全部取消”，而是：

> **用户的新意图是否应该覆盖已经过时的 Agent 后续计划。**

## 4. 实验结果

> **待实际验证后填写。**

### A0

- 用户纠偏后，旧动作继续发生是否会产生明显困惑：
- 是否出现“我的修改到底有没有生效”的不确定感：
- 新旧路线连续出现是否影响理解：
- 是否存在实际上可以接受旧计划继续完成的情况：

### A1

- 旧计划停止后，交互是否更符合用户预期：
- 哪些已经执行的地图状态应该保留：
- 哪些待执行动作应该失效：
- 是否需要明确反馈“已按新要求调整”：
- 是否出现过度取消、重新计算过多等新问题：

### 当前判断

> 待验证后填写。

实验不预设“A1 永远正确”。

如果用户补充的信息与当前任务无关，或者旧动作已经完成且仍然有效，就不应该机械地全部取消。

## 5. 最终沉淀

本实验最终需要回答的不是“Interrupt 功能做出来了吗”，而是：

> **当用户与 Agent 同时操作一个持续变化的 GUI 时，用户主动纠偏后，旧计划和已有状态应该如何处理？**

### 5.1 Interaction Pattern

如果实验支持 A1，可以形成候选模式：

#### User Correction Supersedes Pending Plan

```text
Agent Acting
↓
User Correction
↓
Invalidate Stale Pending Plan
↓
Preserve Still-valid State
↓
Reconcile Latest Intent + GUI State
↓
Agent Re-plan
↓
Continue
```

含义：

> **用户对当前任务目标、约束或选择进行明确纠偏后，依赖旧条件且尚未执行的 Agent 计划应失效；Agent 应基于最新用户意图和最新 GUI 状态继续。**

它同样不应该只属于地图。

例如：

```text
地图
“别走北坡，改从东侧绕”
→ 旧路线计划失效
→ 基于新约束重新预览

表格
“不要筛掉离线设备”
→ 尚未执行的旧筛选条件失效
→ 基于新条件更新结果

甘特图
“这个任务不能提前”
→ 原来的自动排期方案失效
→ 保留其他已确认调整并重新计算

工作流
“这个节点先不要重试”
→ 待执行重试计划失效
→ 从最新流程状态继续
```

### 5.2 Design Principle

基于实验，可以形成以下候选原则：

> **当用户的新输入明确改变当前任务的目标、约束或选择时，用户意图应优先于 Agent 尚未执行的旧计划；Agent 应从最新用户意图与最新共享 GUI 状态继续，而不是完成已经过时的计划。**

同时需要避免另一个极端：

> **用户纠偏不等于无条件清空所有已有状态。**

因此应区分：

```text
仍然有效的已完成状态
→ 保留

依赖旧条件的待执行计划
→ 失效

已经造成不可逆影响的操作
→ 不能简单取消，需要其他恢复机制
```

### 5.3 Boundary

**适合：**

- Agent 正在执行多步 GUI 操作；
- 用户的新输入明确改变任务目标或约束；
- 后续尚有依赖旧条件的待执行动作；
- 继续旧计划会产生明显无效结果或状态冲突。

**可能不需要中断旧计划：**

- 用户输入与当前任务无关；
- 用户只是补充说明，但不改变当前计划；
- 当前动作即将完成且结果仍然有效；
- 用户只是浏览或移动界面，没有表达语义上的任务纠偏。

**需要更强机制：**

如果旧操作已经：

```text
不可逆
产生外部副作用
涉及审批
已经提交业务系统
```

则不能只靠“旧计划失效”处理，而可能需要：

```text
Confirm
Cancel Request
Compensation
Rollback
Recovery
```

这些应进入后续独立实验，而不是塞进 EXP-003。

## 6. 下一步

实验结束后根据结果决定下一步：

```text
A0 也没有明显问题
→ 收窄“用户纠偏必须立即中断”的假设

A1 明显更合理
→ 固化 User Correction Supersedes Pending Plan
→ 提炼 Design Principle 与 Boundary

A1 仍然产生状态混乱
→ 下一步重点验证“用户直接操纵 GUI 后，Agent 如何感知最新状态”

发现真正的问题是不可逆操作
→ 不继续扩 Interrupt
→ 单独进入 Confirm / Recovery 类实验
```

最终需要回答的是：

> **当用户主动改变方向时，Agent 应该如何让出控制权，并从用户刚刚建立的新状态继续协作？**
